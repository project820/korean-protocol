# HTTPS 갱신과 오프라인 유지를 확인했다

> **과거 기록을 보존한다.** 아래 버전·검증 수치·미완료 항목은 작성 당시의 상태다. 현행 0.7의 사용법은 [설치 안내](../../INSTALL.md), 확인 범위는 [현재 상태](../status/requirements.md)를 따른다. 과거 결과를 0.7의 재검증으로 계산하지 않는다.

[실제 실행 기록](https-proxy-smoke.json)의 16단계가 통과했다. Python 3.11.15와 OpenSSL 3.5.6에서 임시 로컬 TLS 서버의 서명된 콘텐츠를 설치·갱신했으며, 호스트 시작 wrapper도 0.2.0에서 0.2.1로 자동 갱신했다. 버전 번호와 키는 시험용이며 실제 공개 릴리스가 아니다.

다음 명령은 저장소 루트에서 실행했다. 이미 설치된 Python 3.11을 사용했으며 의존성을 추가하지 않았다.

```sh
python3.11 tests/manual_https_smoke.py --runtime-root . --via-local-proxy --output docs/distribution/https-proxy-smoke.json
```

배포 런타임의 HTTPS 443 정책과 TLS 검증은 변경하지 않았다. 시험용 CONNECT 프록시는 `localhost:443`만 받아 임시 TLS 서버의 loopback 포트에 암호화된 바이트를 전달한다. 다른 주소의 CONNECT 요청은 거부하며, 프록시·CA 설정은 시험 subprocess에만 전달한다. 사용자 인증서 저장소·전역 지침·예약 작업은 변경하지 않았다.

검증한 동작은 다음과 같다.

- 서명된 로컬 0.2.0 설치와 HTTPS 0.2.1 갱신이 통과했다.
- 잘못된 CA 파일과 정상 형식의 다른 CA를 사용한 요청은 모두 TLS 단계에서 실패했고 HTTP GET과 설치본 변경이 없었다.
- HTTPS로 받은 잘못된 릴리스 서명은 종료 코드 5로 거부했고 설치본을 유지했다.
- 별도의 초기 설치에서 `run` wrapper가 원격 파일 9개를 받아 서명된 0.2.1로 갱신하고 호스트 명령을 실행했다.
- TLS 서버를 종료한 뒤 수동 갱신은 네트워크 오류를 반환했고 기존 프로필과 두 사전은 유지됐다. 자동 갱신을 끈 뒤의 오프라인 wrapper도 실행됐다.
- 설치 관리 블록의 사전 경로는 활성 캐시를 가리켰고 두 사전의 해시가 현재 원본과 일치했다.

독립 Astra 검토자는 스크립트 구문, 실행 기록의 16개 예상 종료 코드, 현재 스크립트·런타임 해시를 대조해 차단 결함이 없다고 판정했다. 검토자는 전체 시험을 다시 실행하지 않았으며 그 검토를 별도의 TLS 재실행으로 계산하지 않는다.

## Python과 환경의 차이를 남긴다

macOS 기본 Python 3.9.6·LibreSSL 2.8.3에서는 `SSL_CERT_FILE`의 임시 CA 경로가 조회됐지만 기본 SSL 컨텍스트에는 시스템 인증서 128개가 로드됐고 시험 서버의 인증서를 거부했다. 같은 CA를 명시한 진단용 컨텍스트에는 인증서 1개가 로드됐다. [실패·진단 기록](https-proxy-python39-failure.json)을 보존하며 Python 3.9의 임시 CA 방식이 통과했다고 표시하지 않는다. 실제 성공 시험은 기본 컨텍스트를 사용하는 Python 3.11에서 수행했고 런타임에 별도 인증서 검증 우회를 넣지 않았다. 이 관측만으로 Python 3.9의 모든 공개 HTTPS 연결이 실패한다고 판단하지 않는다.

[직접 443 바인딩 시험](https-smoke-root.json)은 EACCES로 차단된 과거 기록이다. 이번 시험은 임시 프록시를 사용하므로 직접 443 바인딩이나 공개 서버 운영의 성공을 입증하지 않는다. 실제 발행자 키·공개 릴리스 endpoint·launchd 등록·모델의 전체 사전 읽기·언어 이해도 효과는 별도 검증이 필요하다.

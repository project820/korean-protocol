# Korean Protocol 초기 규약

> **0.1 초기안을 보존한다.** 아래 12개 후보 규칙은 현재 적용 규약이 아니다. 0.7의 72개 규칙은 [한국어 세부 규칙](spec/korean-rules.md), 설치는 [설치 안내](../INSTALL.md)를 따른다.

이 문서는 프로젝트 출발점인 12개 후보 규칙을 보존합니다. 확장 중인 체계는 [전체 목차](spec/toc.md)와 [한국어 세부 규칙](spec/korean-rules.md)을 참조합니다.

이 문서는 한국어의 뜻을 정확하게 전하는 간결한 표현 규칙을 제안합니다. 버전은 **0.1 초안**이며, 작성일은 **2026년 10월 12일**입니다.

규칙은 한국어 LLM 답변과 업무·기술 문서의 지시·보고·경고·설명에 우선 적용합니다. 문학·광고·일상 대화의 표현을 같은 기준으로 제한하지 않습니다.

## 적용 원칙

이 초안에서 **단정한 문체**는 불필요한 우회와 반복을 줄이고 문장의 뜻과 끝맺음을 분명하게 하는 문체를 뜻합니다. 불확실한 내용을 사실처럼 단정하는 것은 이 목표에 어긋납니다.

규칙을 적용할 때에는 뜻의 보존을 먼저 확인합니다. 짧게 고친 문장이 사실·조건·책임·확실성을 바꾸면 채택하지 않습니다. 이미 필요한 뜻을 분명하게 전하는 문장은 유지합니다.

아래의 명령형은 초안을 적용할 때 사용할 편집 기준입니다. 각 규칙과 예문의 효과는 아직 독자 실험으로 검증하지 않았습니다. 연구에서 직접 확인한 내용과 설계상 판단은 [연구 근거](research-basis.md)에서 구분합니다.

예문은 규칙을 설명하기 위해 구성했습니다. 대체문은 적힌 적용 조건을 전제로 하며, 문맥에 없는 사람·수치·절차·원인을 보충하지 않습니다.

<a id="kp-01"></a>
## KP 01 뜻을 유지한다

표현을 고쳐도 말하는 내용과 문장의 역할은 유지한다.

사실, 부정, 조건, 수량, 시점, 담당 주체, 확실성의 차이를 확인한다. 허락을 명령으로 바꾸거나 진행을 완료로 바꾸지 않는다.

| 원문 | 판단 |
| --- | --- |
| 파일을 삭제해도 됩니다. | 허락을 뜻한다. “파일을 삭제하세요”로 바꾸면 지시가 되므로 채택하지 않는다. |
| 검토를 진행했습니다. | 검토가 끝났다는 뜻으로 확정하지 않는다. “검토를 마쳤습니다”로 바꾸려면 완료 사실을 확인해야 한다. |
| 문제가 있을 수 있습니다. | 문제의 가능성을 나타낸다. “문제가 있습니다”로 바꾸면 확실성이 달라진다. |

원문의 뜻을 결정할 정보가 없으면 대체문을 확정하지 않는다. 필요한 내용을 작성자나 확인 가능한 자료에서 찾는다.

<a id="kp-02"></a>
## KP 02 행동을 직접 서술한다

같은 행동을 더 간단한 서술어로 나타낼 수 있으면 우회적인 구성을 줄인다.

| 원문 | 대체문 |
| --- | --- |
| 결과에 대한 확인을 수행했습니다. | 결과를 확인했습니다. |
| 이 기능을 사용하는 것이 가능합니다. | 이 기능을 사용할 수 있습니다. |

위 대체문은 확인한 범위와 기능의 의미가 같을 때 적용한다. “시작하다”, “진행하다”, “마치다”가 행동의 단계를 구분하면 그 뜻을 남긴다.

“검토 완료”처럼 화면이나 목록의 상태를 나타내는 표현은 그 자리에서 이해되면 유지한다. 모든 명사형을 문장으로 늘리지 않는다.

<a id="kp-03"></a>
## KP 03 같은 개념은 같은 이름으로 부른다

한 문서나 대화에서 같은 대상을 가리킬 때에는 이름을 일관되게 쓴다.

화면에 표시된 기능, 파일, 장비, 절차를 가리키면 독자가 실제로 찾을 수 있는 이름을 사용한다. 표현을 다양하게 보이게 하려고 이름을 바꾸지 않는다.

예를 들어 화면의 기능명이 “프로젝트”이면 같은 대상을 가리키는 안내에서 “작업 공간”과 번갈아 쓰지 않는다. 두 기능이 실제로 다르면 각각의 이름을 유지한다.

이름 변경 자체를 설명하거나 두 용어를 비교할 때에는 두 이름을 함께 쓸 수 있다. 단어 하나의 뜻을 한국어 전체에서 하나로 제한하는 규칙은 아니다.

<a id="kp-04"></a>
## KP 04 익숙하면서 정확한 말을 고른다

같은 뜻을 전하는 말 중에서 해당 독자가 쉽게 알아들을 표현을 선택한다.

| 적용 조건 | 원문 | 대체문 |
| --- | --- | --- |
| 같은 달력을 가리키는 일상적인 날짜 안내이다. | 익일에 발송합니다. | 다음 날 발송합니다. |
| 화면의 기능명이 “업로드”이며 독자가 알고 있다. | 파일을 업로드하세요. | 기능 이름을 유지한다. |

전문어가 개념을 정확히 구별하거나 독자에게 익숙하면 유지한다. 낯선 용어의 설명은 이해에 필요한 위치에서 제공하고, 이미 설명한 내용을 매번 반복하지 않는다.

한자어 여부나 글자 수만으로 대체어를 정하지 않는다. 다른 항목과의 구별에 필요한 말도 줄이지 않는다.

<a id="kp-05"></a>
## KP 05 생략해도 알 수 있는지 확인한다

독자가 문맥에서 주체와 대상을 하나로 알아볼 수 있으면 생략한다. 후보가 여럿이거나 주체가 바뀌면 이름을 밝힌다.

한 사람에게 하는 “파일을 저장하세요”라는 지시에 “당신은”을 덧붙일 필요는 없다.

다음 예에서는 “그가”의 대상이 이 대리라는 사실이 확인되어 있다.

| 원문 | 대체문 |
| --- | --- |
| 김 대리가 이 대리에게 초안을 전달했습니다. 그가 검토했습니다. | 김 대리가 이 대리에게 초안을 전달했습니다. 이 대리가 검토했습니다. |

누가 검토했는지 확인되지 않았다면 이름을 임의로 넣지 않는다. 주체를 대비하거나 책임을 강조해야 하면 이름을 밝힌다. 문장을 단독으로 읽을 때와 앞 문맥을 함께 읽을 때의 차이도 고려한다.

<a id="kp-06"></a>
## KP 06 수식 관계와 문장 구조를 정돈한다

꾸미는 말이 어느 대상을 설명하는지 분명하게 놓는다. 관계가 겹쳐 뜻을 따라가기 어려우면 문장을 나눈다.

다음 예는 사용자가 지난주에 요청했고, 담당자가 오늘 수정했다는 뜻이 확인된 경우이다.

| 원문 | 대체문 |
| --- | --- |
| 담당자가 오늘 수정한 사용자가 지난주에 요청한 문서를 확인하세요. | 사용자가 지난주에 요청한 문서를 담당자가 오늘 수정했습니다. 그 문서를 확인하세요. |

문장을 나눌 때에도 대상과 조건의 연결을 유지한다. 원인·예외·동시 행동을 떨어뜨려 놓아 뜻이 달라지면 나누지 않는다.

부정의 범위가 불분명한 문장도 의도를 확인한 뒤 고친다. 이 초안은 문장 길이의 고정 상한이나 관형절의 일괄 금지를 두지 않는다.

<a id="kp-07"></a>
## KP 07 지시의 조건과 순서를 연결한다

지시에는 실행할 행동을 나타낸다. 조건이 행동을 결정하면 그 행동과 함께 쓰고, 순서가 필요한 절차는 순서대로 제시한다.

| 원문 | 대체문 |
| --- | --- |
| 오류가 발생한 경우에는 작업을 중단해야 합니다. | 오류가 나면 작업을 중단해야 합니다. |

여러 단계를 나눌 때에는 각각을 실행할 시점을 분명히 한다. 원래 함께 해야 하는 행동은 같은 단계에 두거나 동시성을 명시한다.

예를 들어 “잠금 버튼을 누른 상태에서 덮개를 여세요”를 “잠금 버튼을 누르세요. 덮개를 여세요”로 고치면 버튼을 계속 눌러야 한다는 조건이 사라진다. 이 수정은 채택하지 않는다.

<a id="kp-08"></a>
## KP 08 가능성과 문장의 기능을 구분한다

가능성·능력·허락·의무를 구별하고, 지시·보고·경고·설명의 목적에 맞는 표현을 사용한다.

| 표현 | 전달하는 뜻 |
| --- | --- |
| 문제가 있을 수 있습니다. | 문제의 가능성을 알린다. |
| 이 장비는 이 형식을 읽을 수 있습니다. | 장비의 기능을 설명한다. |
| 파일을 삭제해도 됩니다. | 삭제를 허락한다. |
| 파일을 삭제해야 합니다. | 삭제의 필요나 의무를 말한다. |

“수 있습니다”를 약한 표현이라는 이유로 삭제하지 않는다. 불확실한 내용을 짧게 전달할 수 있으면 그대로 쓴다.

“문제가 있을 수 있습니다”를 “동시 접속 시험을 하지 않아 최대 접속 수를 확인하지 못했습니다”로 바꾸지 않는다. 두 문장은 각각 위험의 가능성과 시험·확인 상태를 말한다.

불확실성의 이유나 확인 방법은 독자의 판단에 필요할 때 설명한다. 모든 가능성 문장 뒤에 설명이나 확인 약속을 붙이지 않는다.

<a id="kp-09"></a>
## KP 09 행동 기준이 없으면 확인한다

독자가 실행할 행동을 결정해야 하는 지시에서는 기준이나 참조할 절차를 제공한다.

“오류를 적절히 처리하세요”의 “적절히”가 무엇을 뜻하는지 공유되어 있는지 확인한다. 기준이 없으면 표현을 고치는 것만으로 지시를 완성할 수 없다.

| 상황 | 처리 방법 |
| --- | --- |
| 앞서 정한 오류 처리 절차가 기준이다. | “오류 처리 절차에 따라 처리하세요”처럼 실제 절차를 가리킨다. 문서 안에 절차가 여럿이면 이름을 밝힌다. |
| 처리 기준이 정해지지 않았다. | 어떤 행동이 필요한지 확인한 뒤 지시를 작성한다. 재시도·삭제·알림 등의 행동을 임의로 넣지 않는다. |
| 독자가 방법을 선택하도록 맡기는 지시이다. | 필요한 목적과 제약을 전달하고 선택할 여지를 남긴다. 불필요한 세부 절차를 강제하지 않는다. |

이 규칙은 “적절히”라는 단어 자체를 금지하지 않는다. 독자가 판단할 수 있는 정보가 있는지를 확인한다.

<a id="kp-10"></a>
## KP 10 보고는 필요한 결과부터 말한다

진행 상황이나 결과를 묻는 답변에서는 독자가 알고 싶은 상태를 먼저 말한다. 상태를 바꾸는 범위와 제한은 함께 밝힌다.

다음 예는 파일은 저장됐고 서버 반영은 아직 되지 않았다는 사실이 확인된 경우이다.

| 원문 | 대체문 |
| --- | --- |
| 서버 반영은 아직 안 됐고, 파일은 저장됐습니다. | 파일은 저장됐습니다. 서버에는 아직 반영되지 않았습니다. |

파일 저장 여부를 묻는 문맥에서는 위 순서를 사용할 수 있다. 서버 반영 여부가 질문의 중심이면 서버 상태부터 말한다.

“처리했습니다”라고 보고할 때에는 문맥에서 처리 대상과 단계가 식별되는지 확인한다. 실제 실행, 결과 확인, 앞으로 할 일을 혼동하지 않는다.

예상하지 못한 문제나 요청 범위를 바꾸는 제한이 결론에 영향을 주면 뒤로 숨기지 않는다. 설명·교육·창작까지 모든 글을 결과 보고 형식으로 바꾸지는 않는다.

<a id="kp-11"></a>
## KP 11 필요한 만큼 설명한다

독자가 내용을 이해하거나 다음 판단을 하는 데 필요한 정보를 제공한다. 같은 결론, 이미 공유된 배경, 문서의 목적과 관계없는 설명은 반복하지 않는다.

독자가 짧은 경고를 이해했다면 근거를 늘리기 위해 새 상황을 만들지 않는다. 반대로 처음 보는 절차나 판단에 중요한 조건은 짧게 쓰려는 이유로 빼지 않는다.

“문제가 있을 수 있습니다”가 분명한 경고로 이해되는 문맥과, “어떤 문제가 생기나요”에 답해야 하는 문맥을 구분한다. 뒤의 질문에는 확인된 문제를 설명해야 하지만, 그 정보가 없다는 이유로 앞의 경고 자체를 문법적 오류로 판정하지 않는다.

수치를 쓸 때에는 필요한 단위·기준·범위를 남긴다. “응답 시간이 2초에서 1초로 줄었습니다”의 비교 기준을 빼서 개선 폭을 다르게 전달하지 않는다.

<a id="kp-12"></a>
## KP 12 끝맺음과 어조를 상황에 맞춘다

같은 종류의 문장은 어조를 일관되게 유지하고, 문장의 역할이 드러나게 끝맺는다.

일반적인 안내에서는 “저장하세요”, 상태 보고에서는 “저장했습니다”, 확인 요청에서는 “저장했나요”처럼 목적에 맞는 표현을 선택할 수 있다. 정중함을 없애기 위해 요청을 명령으로 바꾸지 않는다.

“설정이 저장되었습니다”는 결과에 초점을 둔 알림으로 사용할 수 있다. 능동문으로 고치기 위해 알려지지 않은 행위자를 넣지 않는다.

화면 상태·표·제목의 짧은 표현은 해당 위치에서 이해되면 유지한다. 이 초안은 모든 문장에 같은 종결어미를 강제하지 않는다.

## 어휘를 기록하는 방법

어휘는 단어 하나의 허용·금지 목록으로만 관리하지 않는다. 뜻과 결합 표현, 분야, 독자를 함께 기록한다.

초기 항목은 다음처럼 작성할 수 있다. 아래 표는 기록 형식의 예시이며 승인 어휘 사전은 아니다.

| 표현 | 사용할 뜻과 조건 | 구별할 내용 |
| --- | --- | --- |
| 저장하다 | 파일이나 설정을 저장하는 행동을 나타낸다. | 서버 반영·외부 공개까지 끝났다는 뜻으로 확대하지 않는다. |
| 검토를 마치다 | 검토가 끝났다는 사실을 나타낸다. | 검토를 시작하거나 진행했다는 보고와 구별한다. |
| 수 있다 | 문맥에 따른 가능성이나 능력 등의 뜻을 나타낸다. | 뜻을 확인하지 않고 삭제하거나 확률 숫자로 바꾸지 않는다. |
| 적절히 | 공유된 기준이나 허용된 판단에 맞춘다는 뜻으로 쓴다. | 행동을 정해야 하는 독자에게 기준이 없으면 보완한다. |

새 어휘 항목에는 실제 사용 문맥, 권장 표현, 예외, 대체하면 뜻이 달라지는 반례를 함께 남긴다.

## 초안을 검토하는 방법

문장을 바꾼 뒤에는 다음을 확인한다.

1. 원문의 사실과 조건, 확실성, 문장의 역할이 유지됐는지 확인한다.
2. 독자가 대상과 관계를 알아볼 수 있는지 문맥과 함께 읽는다.
3. 실제로 읽기 편해졌는지 원문과 비교한다. 짧아진 글자 수만으로 판정하지 않는다.
4. 원문 유지가 더 나으면 수정하지 않은 사례로 기록한다.

의미가 바뀐 수정은 채택하지 않는다. 효과가 불분명한 수정은 후보로 남겨 독자 시험에서 비교한다. 규칙 준수 여부와 실제 이해도는 별도로 평가한다.

규칙의 변경 제안에는 해당 규칙 번호, 원문과 문맥, 대체문, 유지할 뜻, 적용되지 않는 반례를 포함한다. 번호는 검토와 개정을 추적하기 위한 식별자로 사용한다.

# 기능 대응과 완료 판정 정책

Korean Protocol의 STE 기능 대응 목표는 ASD-STE100 Issue 9 작성 규칙 53개 중 최소 48개를 한국어로 완전히 설계하고 검증하는 것이다. 이 비율은 영어 규칙의 문면 일치율, 번역률, 원문 분량의 재현율, 사전 전체의 충족률 또는 LLM의 준수율을 뜻하지 않는다.

## 0.7.0의 현재 상태를 확인한다

현행 `specification/ste-crosswalk.json`은 설계(`designed`) 49개·검증(`verified`) 0개·부분(`partial`) 4개·미연결(`unmapped`) 0개다. 설계 대응률은 49/53(92.45%)이고 검증 대응률은 0/53이다. 설계 90% 기준은 충족하지만 독립 검증 90% 목표는 미달이다.

V7 r2를 반영한 원본은 `0.7.0-draft`다. 과거 0.3.0의 독립 기능 검토는 변경 전 해시에 대한 기록으로 보존하며 현행 검증 점수에 포함하지 않는다. 서명 콘텐츠 `0.7.0`의 발행과 사용자 패키지 `v0.7.0`의 출시는 이 검증 상태를 바꾸지 않는다. [현행 상태](../status/requirements.md)와 [과거 근거](../status/research-evidence.md)를 구분해 읽는다.

## 1. 원본과 분모를 고정한다

비교 원본은 [ASD-STE100 Issue 9 공식 PDF](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf)이며 발행일은 2025년 1월 15일이다. 2026년 10월 12일에 확보한 원문의 제1부 각 절 요약과 본문 규칙 표제를 대조했다. 원본 9개 절의 식별자 집합은 다음과 같다.

| 원본 절은 다음 ID를 포함한다. | 규칙 수는 다음과 같다. |
| --- | ---: |
| 1절은 1.1부터 1.14까지 포함한다. | 14 |
| 2절은 2.1부터 2.2까지 포함한다. | 2 |
| 3절은 3.1부터 3.7까지 포함한다. | 7 |
| 4절은 4.1부터 4.5까지 포함한다. | 5 |
| 5절은 5.1부터 5.5까지 포함한다. | 5 |
| 6절은 6.1부터 6.6까지 포함한다. | 6 |
| 7절은 7.1부터 7.3까지 포함한다. | 3 |
| 8절은 8.1부터 8.7까지 포함한다. | 7 |
| 9절은 9.1부터 9.4까지 포함한다. | 4 |
| 전체는 고유 ID 53개를 포함한다. | 53 |

변경 이력에 등장하는 구판 2.3은 Issue 9의 현행 규칙으로 세지 않는다. 해당 기능은 현행 4.5에서 비교한다. 영어에만 존재하는 형태나 한국어에 직접 대응하지 않는 문법도 분모에서 제외하지 않는다. 새 Issue를 비교하려면 별도 기준선과 변경 내역을 만들고, 이전 53개 기준의 결과를 덮어쓰지 않는다.

비교표는 원본 식별자, 독자적으로 붙인 짧은 기능명, 한국어 설계, 실제 규칙 ID, 상태, 증거와 공백을 기록한다. 원문 규칙 전체, 해설, 예문과 사전을 복제·번역해 대체 문서를 만들지 않는다. 원본의 세부 요구를 확인할 때에는 공식 원문을 참조한다.

## 2. 상태를 증거에 따라 구분한다

`specification/ste-crosswalk.json`의 `status`는 아래 네 값만 사용한다. 항목의 제목이나 설계 문장이 존재한다는 이유로 `designed`를 부여하지 않는다.

| 상태는 다음 뜻을 갖는다. | 이 상태를 부여하는 조건은 다음과 같다. |
| --- | --- |
| `unmapped`는 실제 규칙 연결이 없다는 뜻이다. | 원본 기능을 확인했어도 유효한 `target_rule_ids`가 없으면 이 상태를 유지한다. |
| `partial`은 일부 기능만 연결됐다는 뜻이다. | 실제 규칙은 있지만 세부 기능·조건·예외·한국어 적용 방식 중 하나 이상이 빠져 있다. |
| `designed`는 완전한 기능 대응 설계가 있다는 뜻이다. | 실제 규칙 ID, 적용 조건, 예외, 판정 절차, 문맥이 있는 양호·부적합·원문 유지 용례를 모두 연결하고, 원본 기능의 모든 요소를 대조한 설계 검토를 기록한다. |
| `verified`는 기능 대응 설계의 독립 검토가 통과했다는 뜻이다. | `designed` 조건에 더해 규칙·사례를 독립 검토하고, 기능 보존·예외·오용 판정 결과와 검토자·대상 파일 해시·재현 방법을 기록한다. |

미해결 공백이 핵심 기능을 막으면 `verified` 또는 `designed`로 승격하지 않는다. `verified`는 해당 비교 기능의 검증이며 전체 모델·분야·독자에게 효과가 입증됐다는 뜻이 아니다. 새 규칙 또는 예외 변경이 기존 증거의 전제를 바꾸면 해당 항목을 `designed` 이하로 낮추고 재검증한다.

`evidence`는 실제 파일·규칙·용례·결과를 연결하며, `verified`의 근거는 아래의 기계 판독 계약을 따른다. 공식 원문 위치는 기능을 확인한 증거로 사용할 수 있지만 한국어 대응을 검증한 증거로 계산하지 않는다. 계획이나 앞으로 실행할 명령은 검증 증거가 아니다. `gaps`에는 누락된 기능, 아직 연결하지 않은 자료, 실행하지 않은 시험과 이를 해소할 작업을 적는다.

`verified` 항목의 `evidence`에는 `{"path":"실제 검토 JSON의 저장소 상대 경로","kind":"functional-review","result":"pass"}` 형식의 객체가 있어야 한다. 임의의 `pass` 문자열이나 파일 존재만으로 통과시키지 않는다. 해당 JSON은 다음 내용을 담아야 한다.

- `reviewed_rules_sha256`는 검토한 `specification/rules.json` 파일의 SHA-256 해시와 일치해야 한다.
- `reviewed_cases_sha256`는 검토한 `examples/rule-cases.json` 파일의 SHA-256 해시와 일치해야 한다.
- `independent_cases_path`는 별도로 작성한 `evaluation/functional-cases.json`을 가리키며 `independent_cases_sha256`는 해당 파일의 SHA-256 해시와 일치해야 한다.
- `reviewed_spec_path`는 `docs/spec/korean-rules.md`를 가리키며 `reviewed_spec_sha256`는 실제로 검토한 상세 규범 파일의 SHA-256 해시와 일치해야 한다. 규칙 JSON이 참조하는 문장 경계·측정 절차도 이 파일 해시로 고정한다.
- `reviews` 배열의 각 항목은 `ste_id`, `target_rule_ids`, `verdict`, `rationale`, `case_ids`, `reviewer`를 포함해야 한다.
- `verdict`는 `pass` 또는 `fail`이며, 대응표의 원본 ID와 실제 규칙 ID에 일치하는 `pass` 검토가 해당 상태를 뒷받침해야 한다.
- `case_ids`는 독립 사례의 실제 ID를 가리키며, 각 사례의 `ste_ids`에 해당 검토의 원본 ID가 있어야 한다. `rationale`은 그 사례와 규칙이 원본 기능의 조건·예외를 충족하는 이유를 설명해야 한다.
- `reviewer`는 검토 주체를 식별해야 하며, 검토 기록은 작성자의 자기 검토와 독립 검토를 구분해야 한다.

해시는 실제 파일 바이트를 기준으로 계산하고 대상이 바뀌면 이전 검토를 현재 버전의 증거로 사용하지 않는다. 이 계약이 확인하는 것은 기능 대응 설계의 검토 결과이며, 실제 LLM이 문장을 생성해 의미를 보존했다는 결과나 사람이 더 잘 이해했다는 결과가 아니다. 실제 LLM과 독자의 성능은 제5절의 별도 관문에서 검증한다.

독립 사례에는 문맥, 입력, 기대 판정, 허용 대안, 거부 대안과 이유를 기록한다. `keep`의 허용 대안은 입력과 같고 `clarify`의 허용 대안은 `null`이며 `revise`에는 의미를 보존한 대안이 있어야 한다. 사용자 지정 공통 회귀 문장이 작성자 사례에도 있으면 이를 독립 사례로 중복 계산하지 않고 `independent: false`로 표시하여 검토의 `case_ids`에서 제외한다.

작성자 사례와 독립 사례 모두 입력·문맥만으로 기대 판정을 평가할 수 있어야 한다. 잘못된 편집 후보를 복구하는 사례는 실제 원문, 확인된 문맥, 입력이 후보라는 사실과 교정 과제를 같은 사례에 담아야 한다. “정상 예문의 뜻과 같다”처럼 외부 정답을 숨겨 놓고 원문에 없는 사실을 복구하도록 요구하면 기능 검토를 통과시키지 않는다. 작성자 예문에서 파생한 사례는 독립 사례 수에 포함하지 않으며, 같은 입력·문맥에 상충한 판정이 있으면 그 차이를 해소해야 한다.

대응표의 `target_rule_ids`는 실제로 기능을 충족하는 규칙만 연결한다. 규칙의 넓은 참고 범위인 `ste_refs`가 해당 기능에 대한 완전 대응 증거는 아니다. 연결한 규칙에 원본 참조가 없는 경우는 참조 오류이며, 참고 참조는 있지만 실제 대응에 채택하지 않은 규칙은 관련 참조 공백으로 보고한다.

## 3. 한국어의 기능 대응을 심사한다

비교 단위는 원본 규칙 하나가 수행하는 작성·판정 기능 전체이다. 하나의 한국어 규칙이 여러 원본 항목을 충족할 수 있지만, 원본 항목마다 별도의 기능 대조와 증거를 남겨야 한다. 한국어 규칙 여러 개가 원본 한 항목을 나누어 맡으면 필요한 규칙 모두가 충족돼야 그 항목을 완전 대응으로 센다.

한국어에 없는 영어 형태를 단지 “해당 없음”이라고 적으면 완전 대응이 아니다. 원본이 방지하는 혼동과 수행하는 통제 기능을 명시하고, 한국어에서 그 기능을 담당하는 규칙·판정 절차·예외·용례를 제시한다. 비교 가능한 기능이 없다고 판단한 항목은 공백으로 공개하고 분모에는 남긴다.

다음 구별을 반드시 적용한다.

- 영어의 활용 제한은 한국어의 시상·양태를 삭제할 근거가 되지 않는다. 활용·보조용언·관형형의 의미 차이를 보존하면서 모호한 구성을 판정해야 한다.
- 영어의 관사 기능은 한국어의 조사·지시어·명칭 재사용·생략 조건과 비교한다. 모든 한국어 명사에 지시어를 붙이는 방식은 인정하지 않는다.
- 영어의 파생 명사·동사 제한은 한국어의 생산적인 명사화나 `-하다`를 전면 금지하는 방식으로 대응하지 않는다. 의미·품사·결합을 확인하는 체계를 요구한다.
- 문장·문단 길이와 측정 항목은 단순히 “간결하게 쓴다”는 선언으로 충족하지 않는다. 문장 경계, 절·수식 부담, 목록, 괄호, 리터럴, 복합명칭에 관한 재현 가능한 측정 또는 검토 절차를 정의하고 독립 사례로 확인해야 한다.
- 원본의 수치 제한을 유지하지 않는 한국어 설계는 무엇을 측정하고 어떤 기준으로 재검토하는지 명시해야 한다. 고정 어절 상한이 한국어 이해도를 높인다고 근거 없이 주장하지 않는다.
- 측정을 위해 괄호·인용·긴 식별자를 한 묶음으로 세더라도 내부 정보량을 별도로 검사해야 한다. 정보를 묶어서 부담을 숨기는 경우는 적합으로 처리하지 않는다.
- “문제가 있을 수 있습니다”를 일괄 오류로 판정하지 않는다. 불확실성의 삭제, 근거 없는 확률화, 원문에 없는 장문 설명의 추가는 의미 보존 실패로 처리한다.

## 4. 두 대응률을 각각 보고한다

설계 대응률은 `(designed + verified) / 53`이고 검증 대응률은 `verified / 53`이다. 분자는 각 조건을 모두 충족한 고유 원본 항목 수이며 중복 대응을 추가 점수로 세지 않는다. 48/53은 약 90.57%이고 47/53은 약 88.68%이므로 최소 통과 개수는 48개이다.

`partial`과 `unmapped`는 두 분자에 0개로 반영한다. 부분 대응 0.5점이나 분모 축소로 90%를 만들지 않는다. 결과에는 상태별 개수, 원본 절별 분포, 미충족 항목 ID, 부족한 증거와 기준 버전을 함께 표시한다.

48개 설계가 있으면 “설계 대응률 90% 이상”이라고만 보고한다. “검증 대응률 90% 이상”은 실제 `verified`가 48개 이상일 때에만 보고한다. 현재 비교표의 항목 상태와 실제 증거가 결과의 근거이며, 목표치 자체를 달성치로 쓰지 않는다.

## 5. 전체 완료에는 별도 관문을 적용한다

STE 검증 대응률의 통과만으로 전체 규약을 완료하지 않는다. 아래 다섯 관문은 서로 보상할 수 없으며 각각의 결과를 공개한다.

| 관문은 다음 영역을 검증한다. | 통과에는 다음 증거가 필요하다. |
| --- | --- |
| 기능 대응 관문은 원본 53개 작성 기능을 검증한다. | 최소 48개가 `verified`이고, 나머지 항목의 영향과 공백을 공개하며, 핵심 기능의 누락을 총점으로 숨기지 않는다. |
| 어휘 관문은 선언한 분야의 어휘 통제 기능을 검증한다. | 의미·품사·활용·결합·전문 명사·전문 동사·프로젝트 확장·충돌 처리의 규범과 시험이 있고, 별도로 고정한 분야별 평가 문맥에서 승인 의미 사용 충족률을 보고한다. |
| 한국어 관문은 한국어에 필요한 고유 기능을 검증한다. | 조사·논항, 생략·지시 대상, 관형절·수식, 부정·수량, 시상·양태, 피동·사동, 높임·종결형, 조건·동시성마다 정상·실패·원문 유지 독립 사례와 판정 기록이 있다. |
| 실제 LLM 관문은 설치된 규약의 출력 효과를 검증한다. | 지원 모델·버전·설정·프로필과 입력·원출력을 보존하고, 미적용 기준선과 비교해 의미 보존 및 명확성을 평가한 결과가 있다. |
| 배포 관문은 지속 설치와 자동 업데이트를 검증한다. | 지원 환경에서 새 세션 적용, 재시작, 사용자 설정 보존, 오프라인 사용, 업데이트, 버전 고정, 변조 거부, 실패 후 기존 버전 유지와 복구 증거가 있다. |

핵심 기능은 의미 보존, 대상 식별, 필수 조건·동시성·부정, 화행·확실성, 어휘의 승인 의미, 안전 안내의 행동·위험 연결이다. 해당 기능을 누락한 규약은 다른 항목의 점수가 높아도 전체 완료로 판정하지 않는다. 핵심 기능이 미충족인 경우 그 기능과 관련 원본 ID·한국어 규칙 ID를 실패 목록에 명시한다.

어휘의 평가 분모는 선언한 분야·독자·자료에서 추출한 개념별 사용 문맥이며, 사전 항목 수가 아니다. 표본 목록과 승인 의미 매칭 방법을 평가 전에 고정한다. 한국어 문장 전체의 무제한 어휘에 대한 90% 충족을 주장하지 않는다.

실제 LLM 관문에서는 평가 집합, 표본 수, 반복 횟수, 명확성 평가 방식과 성공 기준을 실행 전에 고정한다. 필수 의미 보존 사례에서는 사실 추가·누락, 금지·허락 혼동, 조건·주체 변경, 불확실성 제거의 실패가 없어야 한다. 개선 효과를 주장하려면 별도 독자 평가 또는 독립 평가자가 비교한 이해 정확도·재독·추가 질문 결과를 제시해야 하며, 스키마 검사의 성공만으로 이 관문을 통과시키지 않는다.

평가 설계가 아직 고정되지 않았거나 실제 실행이 없으면 해당 관문은 미검증으로 남긴다. 사용자에게 보여 주는 상태 보고에는 설계 완료, 정적 검사 통과, 로컬 런타임 시험, 실제 환경 검증, 독자 효과 검증을 구분한다.

## 6. 검사와 변경 이력을 남긴다

검사기는 53개 고유 ID의 정확한 집합, 중복·누락, 허용 상태 값, 실제 규칙 참조와 증거 파일 존재를 확인한다. `designed`와 `verified`에 필요한 조건을 형식으로 확인할 수 있는 부분과 사람이 기능을 대조해야 하는 부분을 구분한다. 존재하는 파일 경로만으로 증거 내용의 충분성을 자동 승인하지 않는다.

감사 기록은 대상 릴리스, 대응표 버전, 검토자, 날짜, 판정, 근거와 남은 공백을 포함한다. 동일한 작성자가 자기 용례만 검토한 결과는 독립 검증으로 표시하지 않는다. 규칙 변경 뒤에는 영향을 받는 원본 ID의 상태와 실제 LLM·배포 재검증 필요성을 함께 갱신한다.

# Korean Protocol 의미 단위 어휘사전

이 문서는 0.2.0 초안의 한국어 통제어휘 계약을 정의한다. `lexicon/core.json`은 일반 업무·기술 문맥의 155개 뜻을 담고, `lexicon/domains/software.json`은 소프트웨어·문서관리의 22개 뜻을 더한다. 이 177개 뜻은 사용할 수 있는 **초기 재고**이며 한국어 전체나 기술 분야의 완성 사전은 아니다. 규약의 기능 대응률과 사전의 어휘 완성률은 별개다. 이 재고의 수나 예문 통과를 근거로 사전이 90% 완성됐다고 말하지 않는다.

## 통제하는 단위

사전은 단어 모양보다 **표현과 뜻과 문맥의 결합**을 관리한다. `열다`의 문서 표시와 물리적 개방, `수 있다`의 가능성·능력·허락, `토큰`의 자격 정보와 언어 모델 처리 단위는 별도 항목이다. 한 단어에 한 뜻만 허용하도록 한국어 전체를 제한하지 않는다. 사전에 없는 말도 문맥에 맞으면 사용할 수 있다.

일반어의 뜻을 먼저 관리하고, 전문명사·전문동사·제품 기능명·프로젝트 용어는 분야 사전에서 추가한다. `업로드하다`, `롤백하다`, `브랜치`처럼 독자가 알고 개념을 정확히 구별하는 표현은 한자어나 외래어라는 이유로 바꾸지 않는다. 원자료의 영어 승인 단어 목록을 번역하거나 동의어 치환표로 복제하지 않았다. 정의와 예문은 이 프로젝트의 한국어 편집 설계로 직접 작성했다.

## 파일과 필드

모든 사전 파일은 `schemas/lexicon.schema.json`에 따라 `{schema_version, version, entries}`를 갖는다. `schema_version`은 `1.0`이며 데이터 버전은 `0.2.0-draft`이다. 핵심과 분야 확장은 같은 계약을 사용한다. 첫 배포에 포함되는 확장은 `lexicon/domains/software.json`이다.

| 필드 | 자료형과 의미 |
| --- | --- |
| `id` | `KPL-0001` 또는 `KPL-SW-0001`처럼 변경하지 않는 문자열 식별자이며 전체 활성 사전에서 중복되지 않는다. |
| `lemma` | 단어·구·문법구성을 대표하는 한국어 표제 문자열이다. |
| `sense_id` | `open_document`처럼 소문자 ASCII로 쓰는 의미 식별 문자열이며 표제어와 함께 뜻을 구별한다. |
| `pos` | 한국어 편집용 품사 또는 문법기능을 기록하며 동사·형용사·명사·부사·의존표현·접속표현·관형표현·서술표현 가운데 하나를 쓴다. |
| `meaning` | 이 항목에서 사용하는 뜻을 한국어로 정의한다. |
| `status` | 이 초안에서의 편집 선호를 `preferred`, `allowed`, `restricted`, `deprecated`로 표시한다. |
| `domains` | 한 개 이상의 적용 분야 문자열을 기록하며 `general`은 기본 일반어 범위이다. |
| `forms` | 대표 활용형과 실제 조사 결합형을 문자열 배열로 기록하며 최소 하나를 둔다. |
| `frames` | 대상·주체·조건과 결합하는 표현틀을 문자열 배열로 기록하며 최소 하나를 둔다. |
| `conditions` | 이 뜻의 사용을 판단하는 문맥 조건을 문자열 배열로 기록한다. |
| `avoid_senses` | 해당 항목의 뜻에 포함시키면 안 되는 상태나 의미 확장을 문자열 배열로 기록한다. |
| `alternatives` | 다른 항목을 가리키는 `{entry_id, relation, condition}` 객체 배열을 기록한다. |
| `examples` | `allowed`, `disallowed`, `exception`의 세 배열을 둔다. |
| `provenance` | 정의·예문의 작성 경로 또는 근거 자료를 문자열 배열로 기록하며 최소 하나를 둔다. |
| `since` | 해당 뜻이 도입된 데이터 버전을 `0.2.0`처럼 기록한다. |
| `deprecated_since` | 비폐기 항목에서는 `null`이며 폐기 항목에서는 폐기된 데이터 버전 문자열이다. |

`conditions`, `avoid_senses`, `alternatives`, `examples.disallowed`, `examples.exception`은 해당 기록이 없으면 빈 배열을 쓴다. 빈 문자열로 없음을 표현하지 않는다. `examples.allowed`에는 최소 한 개의 `{context, text}` 객체를 둔다. 부적합 예문과 예외 예문에는 같은 필드에 `reason`을 더한다. `exception`은 문맥을 정해 허용하는 경우를 설명하며 더 높은 우선순위로 모든 규칙을 무효화하는 명령이 아니다.

`pos`는 형태소 분석기의 품사 태그가 아니다. `저장하다`는 단어와 서술 기능을, `진행 중`은 상태 구를, `수 있다`는 문법구성을 대표한다. `의존표현`은 조사·의존명사·복합 서술구성을 함께 관리하는 편집 범주이다. `서술표현`은 `진행 중`과 `관련이 있다` 같은 구의 서술 기능을 기록한다. `-(으)면`은 조건 연결 기능을 기록하며 `-는 한`은 조건의 지속 범위를 연결한다. 형태소별 품사와 단어·구·문법구성의 자동 분류가 필요한 구현은 별도 분석 결과를 둬야 하며 이 값을 그대로 한국어 문법의 단일 품사 체계로 해석하지 않는다.

### 상태와 대체 표현

`preferred`는 해당 뜻과 문맥에서 이 초안이 먼저 제안하는 표현이다. `allowed`는 정확한 전문어·일관된 기존 표현 등을 유지할 수 있다는 뜻이다. `restricted`는 기준·목적·평가 범위가 필요한 뜻을 표시한다. 예를 들어 `안전하다`는 평가 범위를, `평균`은 자료 집합을, `적절하다`는 공유 기준 또는 위임된 재량을 확인한다. 이 상태는 문장이 틀렸다는 자동 판정이 아니다. `deprecated`는 이후 작성에서 이 항목의 사용을 중단하는 편집 상태이며 기존 문서·인용·제품 이름을 일괄 삭제하는 명령이 아니다.

어떤 상태도 전문가의 최종 승인이나 독자 실험의 통과를 뜻하지 않는다. 첫 재고에는 폐기 항목이 없으나 스키마는 폐기 시점과 기존 식별자의 이력 보존을 지원한다. 새 이름의 적용을 승인했을 때 기존 뜻 항목을 폐기 상태로 남기고 대체 항목의 식별자를 기록한다. `since`를 고쳐 과거의 뜻이나 도입 시점을 지우지 않는다.

`alternatives.relation`은 `same_sense` 또는 `contextual`이다. `same_sense`는 같은 뜻을 가리키는 표현 선택이며 대상·범위·사실·양태·문장 기능이 모두 같을 때만 사용한다. `contextual`은 기록된 `condition`을 만족하는 문맥에서 선택 가능한 표현이다. 현재 초기 재고의 여섯 대체 참조는 모두 `contextual`이며 자동 치환 명령이 아니다. `entry_id`는 활성 사전이나 함께 불러온 이력 사전의 실제 항목을 가리켜야 한다. 자기 참조와 확인할 수 없는 참조를 허용하지 않는다.

## 활용형과 조사 결합

`forms`는 모든 어절을 나열한 폐쇄 목록이 아니다. `저장합니다`, `저장했습니다`, `저장하세요`는 대표적인 실현형이고 조사가 결합된 예시는 `파일을`과 `범위를`이며 표제 명사의 받침에 맞춰 선택했다. `forms`에는 조사 선택지 표기나 의미에 맞지 않는 명령형을 넣지 않는다. `frames`는 관계를 설명하는 표현틀이며 실제 출력 어절과 구별한다. 띄어쓰기·시제·높임·부정·연결어미·보조사 조합의 수가 늘어난다는 이유로 수천 개의 형태를 사전에 복제하지 않는다.

검사 도구는 표제어와 활용형 후보를 연결한 뒤 표현틀·문맥·뜻을 다시 확인한다. 형태 분석기가 없거나 후보가 하나로 정해지지 않으면 미등록 또는 미확정으로 남긴다. 표면 문자열이 목록에 없다는 사실만으로 오용을 선언하지 않는다. 접미어 제거만으로 `확인하지 못했습니다`를 `확인했습니다`로 만들거나 `저장될 수 있습니다`를 `저장됐습니다`로 바꾸지 않는다.

문법구성의 표제는 `-(으)면`, `-는 한`처럼 결합 경계를 표시한다. `forms`의 앞 붙임표는 홀로 쓰는 어절이 아니라 결합형임을 뜻하며 `-면`과 `-으면`, `-는 한`과 `-(으)ㄴ 한`의 실제 형태를 구별한다. 이 문법형은 받침과 앞 서술어의 품사에 맞춰 적용하며 `화면`·`도면` 내부의 면이나 `수정한` 내부의 한을 문자열 부분 일치로 인식하지 않는다. 관형어미의 한과 뒤 의존명사 한의 띄어쓰기·구문 연결도 구별한다.

복합 양태 구성은 전체 뜻을 먼저 확인한다. `원인은 설정 오류인 것 같습니다`는 `같다`의 동일 뜻이 아니라 추측 구성이다. `수 없다`의 능력 부재와 정책상 불허는 각각 KPL-0126과 KPL-0154로 판단한다. 가장 긴 문자열 후보가 있다는 이유만으로 뜻이 결정되지는 않으며 문맥·표현틀·주체를 확인한다.

활용 검증에서는 높임과 시제, `안`·`못`·`않다`·`없다`의 부정 범위, `만`·`도`·`부터`·`까지`의 조사 범위, 진행·결과 상태를 별도 축으로 확인한다. `수 있다`의 세 뜻은 문맥과 주체의 권한·능력에 따라 판단하며 확률 수치를 요구하거나 해당 구성을 모두 금지하지 않는다. `문제가 있을 수 있습니다`는 대상이 공유된 경고에서 원문을 유지한다.

## 분야 확장과 프로젝트 용어

확장은 기술용어에 같은 필드를 부여한다. 분야의 정의·고유 이름·독자의 전문 지식을 적용 조건으로 기록한다. 도메인 파일에 일반 사전과 같은 `lemma + sense_id`를 다시 정의하지 않는다. 같은 표면형의 다른 뜻을 추가하려면 새로운 `sense_id`와 새 `id`를 부여한다. 기존 `id`의 뜻을 분야에 따라 바꿔 읽게 하지 않는다.

`software.json`의 `프로젝트`와 `작업 공간`은 서로 다른 기능을 가진 **예시 제품**의 프로젝트 용어이다. 이 예시가 모든 소프트웨어 제품의 정의라고 주장하지 않는다. 실제 제품에서는 화면 기능명과 소유자의 용어표를 참조하고, 동일 이름의 정의가 다르면 실제 제품의 새 의미 항목을 별도로 기록한다. 전문명사의 내부 구성이나 화면 기능명을 임의로 풀어 쓰지 않는다.

사전에 없는 `AcDs` 같은 용어를 작성자가 실제 레코드명으로 지정했다면 그대로 사용할 수 있다. 미등록은 검토 후보이며 오류가 아니다. 대상이 무엇인지 독자의 행동에 필요하고 문맥에서도 찾을 수 없으면 작성자에게 뜻이나 참조 위치를 확인한다. 검사 도구가 이를 아는 일반어로 임의 번역하지 않는다.

### 사용자 지정과 충돌

사용자의 명시적 표현·제품명·독자·문서 목적은 해당 작업에 적용한다. 기존 용어를 유지하라는 지시가 있으면 편집 선호만으로 바꾸지 않는다. 사용자 지정은 출처·범위·대상 독자·유효 버전을 가진 별도 프로젝트 용어 기록으로 관리하며 이번 초안의 파일에 사용자 명령을 전역적으로 덮어쓰지 않는다.

프로젝트 용어가 일반어의 새 뜻이면 새 항목으로 추가한다. 같은 `id` 또는 같은 `lemma + sense_id`로 기존 의미를 덮어쓰려는 확장은 충돌로 중단한다. 같은 표제어가 여러 뜻으로 등록돼도 오류는 아니며 분야와 표현틀로 구별한다. 분야·프로젝트 뜻이 동시에 활성화돼 대상이 구별되지 않으면 `clarify`를 반환한다. 사용자가 표현을 정했어도 불명확한 사실·완료·허락을 다른 뜻으로 확정하는 치환은 채택하지 않는다.

사용자가 해당 문서에서 다른 표현을 의도적으로 지정했을 때에는 그 지시의 문맥을 남기고 해당 문서의 선택에 적용한다. 인용, 파일명, 명령어, 코드 식별자, 문서 제목 안의 표기는 뜻을 설명하는 본문과 구별하여 원형을 보존한다.

## 뜻의 변경과 버전 이력

철자 수정이나 예문 보완은 기존 뜻·식별자를 유지할 수 있다. 사용 뜻의 범위를 넓히거나 좁히고 양태·대상·조건을 바꾸는 수정은 기존 의미를 교체하는 작업이므로 새 의미 항목을 만든다. 이전 항목의 폐기 버전과 대체 관계를 남겨 과거 문서의 해석이 바뀌지 않게 한다. `version` 변경만으로 기존 `id`의 뜻을 바꾸지 않는다.

사전 로더는 JSON 스키마 확인 외에 전체 파일의 ID 중복, `lemma + sense_id` 중복, 대체 참조의 대상 존재, 자기 참조, 사례 참조, 비폐기 항목의 `deprecated_since: null`을 확인한다. 한국어 정의의 뜻이 같은지 또는 바뀌었는지는 문자열 일치 검사만으로 판정하지 않고 개정 비교와 사람의 검토로 확인한다.

## 사례와 검증의 범위

`examples/lexicon-cases.json`은 `{schema_version: "1.0", cases: [...]}`를 사용한다. 각 사례는 `id`, `entry_ids`, `context`, `input`, `expected`, `origin`, `task_type`, `case_type`을 가지며 `expected`는 `decision`, `output`, `reason`을 갖는다. `decision`은 `keep`, `revise`, `clarify` 중 하나다. `keep`의 출력은 입력 그대로이고 `clarify`의 출력은 `null`이다. 의미보존 편집에서 `revise`는 입력의 뜻을 유지하는 대체문이다. 확인된 사실에 따른 후보 정정에서 `revise`는 틀린 주장이나 지시를 바로잡으므로 입력의 잘못된 주장을 보존하지 않으며 정정 근거를 이유에 밝힌다.

현재 파일의 398개 구성 사례 중 177개는 전체 항목과 허용 예문을 연결하는 재고 연결 점검이다. `LEX-KPL-…-KEEP`라는 식별자와 판정 이유의 재고 연결 표시로 구별하며 의미변별 사례 수에서 제외한다. 의미변별 등 작성자 사례는 221개이고 그중 새 `LEX-SEM-…` 177개는 모든 뜻의 의미 경계를 겨냥한 사실정정 `revise` 161개와 `clarify` 16개다. 나머지 44개는 원문 유지, 우회 구성 수정, 양태·조건·동형어·전문어·품사 범위와 활용형의 별도 사례다.

모든 사례의 `origin`은 `author`이며 사전 작성자가 같은 뜻과 의미 경계를 바탕으로 만든 구성 자료다. 이 221건은 별도 작성자의 독립 평가, 외부 코퍼스 또는 LLM 실험 자료가 아니다. 문맥과 판정 이유가 서로 다르다는 사실은 평가의 독립성을 뜻하지 않는다. 구성 예문은 실제 독자나 LLM의 판단을 측정한 결과가 아니다.

양성 사례의 연결은 재고 누락 검사이며 부적합 예문·부정 사례의 폭이나 독자 이해도를 대신하지 않는다.

이미 명확하고 불필요한 우회 구성이 없는 문장이면 `keep`을 반환한다. 뜻·대상·범위·양태·문장 기능을 유지하면서 `확인을 수행하다`, `-는 것이 가능하다` 같은 우회 구성만 줄일 수 있으면 `revise`를 반환한다. `원격 진단이 가능합니다`처럼 이미 직접적인 상태·기능 설명은 같은 기준으로 유지한다.

공유된 기준이 없어서 행동을 결정할 수 없거나 다의어의 대상이 겹치면 `clarify`를 반환한다. 알려지지 않은 완료 사실·확률·주체·원인·조치를 보충해야만 바꿀 수 있는 치환도 확정하지 않는다. 변경 대상이 없으면 단지 미등록 어휘가 있다는 이유로 `clarify`를 남발하지 않는다.

후속 재고는 분야별 실제 문서에서 필요한 뜻을 수집하고 잘못된 결합·오해·용어 충돌 사례를 추가해 확장한다. 빈도·친숙도·이해 정확도·읽는 시간·자연스러움·오탐을 분리해 시험해야 한다. 이번 초안은 한국어학·분야 전문가의 자문, 실제 독자 비교시험, 형태소 분석과 의미 판정의 실행 구현을 마쳤다는 주장을 하지 않는다.


### 작업 유형과 사례 유형

`task_type`은 `inventory_check`, `meaning_preserving_edit`, `candidate_correction` 가운데 하나다. 첫 값은 재고 연결 검사이며 둘째 값은 입력의 뜻·발화목적을 보존하는 편집이다. 셋째 값은 context의 확인된 사실에 맞춰 잘못된 후보를 정정하는 과제다. `LEX-SEM` 177건과 기존 사실정정 4건은 셋째 과제를 명시하며 사전 작성자의 구성 자료로 남긴다.

`case_type`은 `inventory_linkage`, `preservation`, `meaning_preserving_revision`, `factual_correction`, `needs_information` 가운데 하나다. 의미보존 편집은 어휘나 구조를 바꿔도 전달 내용이 같아야 하지만 사실정정은 잘못된 내용 자체를 바꾸는 작업이다. 사실정정 권한이 없는 과제에서는 같은 오류 후보를 임의로 고치지 않고 확인할 정보와 작성자의 결정을 요청한다. 각 사실정정 이유는 구체적인 context 사실과 원래의 의미 경계 이유를 연결하며 단순히 context 기반이라는 문구만 붙이지 않는다.

잘못된 원인·수치·완료 주장을 삭제한 뒤 확인된 관찰이나 상태만으로 요청한 보고가 성립하면 사실정정이 가능하다. 예를 들어 온도 상승과 센서 경고를 같은 시각에 관찰했다는 기록만 있으면 원인 확정 주장을 빼고 그 관찰을 보고한다. 실제 원인을 지정한 보고를 요청했는데 원인 근거가 없다면 보고의 필수 내용이 없으므로 확인이 필요하다. 사용자의 지시가 있어도 미확인 원인이나 수치를 창작하지 않는다.

실행 지시는 보고와 구별한다. 연결 해제 의도가 알려져 있어도 실제 화면 기능명을 사용한 조작 지시가 과제인데 기능명·절차가 없으면 필요한 정보를 확인한다. 반복 횟수와 종료 조건을 반드시 명시하는 실행 지시가 과제라면 그 기준을 지어내지 않는다. 반면 지체 없이 중단한다는 지시가 이미 확인됐으면 임의의 3초 제한만 제거해 해당 지시를 정정할 수 있다.

새 부적합 사례는 알려진 문맥과 불확실한 정보를 구별한다. `revise`의 추가 사실은 context에 실제로 주어진 정보만 쓰고 원인·완료·정책·수치를 추정해서 보충하지 않는다. 확인된 사실에 따른 후보 정정에서 근거 없는 추가 주장을 빼도 요청된 보고나 지시를 완성할 수 있으면 `revise`를 쓴다. 요청된 실제 대상·행동·기준·권한 또는 필수 결과가 미확인이라 완성할 수 없으면 `clarify`와 `output: null`을 쓴다. 177개의 새 부적합 문맥과 판정 이유는 각각 다른 의미 경계를 설명하며 하나의 문장에 단어만 바꾼 틀을 사용하지 않았다.

최종 집계는 핵심 155뜻·분야 22뜻이며 preferred 141개·allowed 30개·restricted 6개이고 deprecated는 0개다. 전체 사례 398개는 keep 201개·revise 174개·clarify 23개이며 재고 연결 점검을 뺀 의미변별 등 작성자 사례 221개는 keep 24개·revise 174개·clarify 23개다. case_type 집계에서 의미보존 수정은 9개이고 사실정정은 165개이며 둘을 같은 의미보존 정답률로 합치지 않는다. `LEX-SEM-…`의 177뜻 연결은 의미 경계별 구성 사례를 갖췄다는 뜻이며 실제 모델의 정답률이나 독자 이해도를 입증하지 않는다.

이 교차 검토 단계는 배포 전 0.2.0 초안의 정의 오류를 정정하는 단계이며 기존 배포 문서의 해석을 바꾸는 뜻 교체와 구별한다. 모델 평가에 사용하는 첫 여덟 뜻의 표제·sense_id·meaning·조건·활용형은 유지했다. 이후 배포된 의미를 바꾸는 개정에는 앞 절의 새 식별자·폐기 이력 정책을 적용한다.

## 두 번째 모델 검토 뒤의 정확성 정정

두 번째 Opus 검토는 사실정정과 의미보존 편집의 혼동을 지적했다. 모든 사례에 task_type과 case_type을 부여하고, 후보 정정 과제의 context와 reason에 허용된 작업 및 구체적인 정정 근거를 적었다. 잘못된 추론을 제거해 확인한 사실만 보고할 수 있는 경우와 실제 조작·수신자·권한·기준을 확인해야 하는 경우를 구별했다. 모든 자료의 origin은 author이며 별도 작성자나 외부 코퍼스에서 독립적으로 수집한 실증 사례라고 표시하지 않는다.

LEX-SEM-0074는 실제 수신자를 알지 못하므로 clarify로 바꿨고 전달 사건을 역할 설명으로 대체하지 않는다. LEX-SEM-0127에서는 문맥에 없던 임시 파일을 제거했다. LEX-SEM-0023에서는 다른 편집자가 행사 수행을 일부 수행으로 바꾼 후보라는 문맥을 밝혔으며 사용자 요청을 무시하는 사례로 남기지 않았다. LEX-SEM-0004·0092·0122와 SEM-SW-0017은 각각 제안을 계획으로 바꾼 표현, 확인을 검토로 올린 표현, 임의 주체, 근거가 문맥에 없는 단위 동일성 주장을 정정했다.

LEX-SEM-0008은 의도가 아니라 화면 기능명·절차가 필요한 조작 지시의 정보 부족을 기록한다. 메타 설명이던 13개 입력은 실제 문서 또는 지시 후보로 바꾸고 출력의 발화목적을 맞췄다. 원인·수치 미확인 사례는 작업 유형에 맞춰 정정 또는 확인의 판정을 일관화했다. LEX-SEM-0070의 앞선 접촉 행동 추가와 LEX-SEM-0024의 단계 수 표기 수정도 그대로 유지했다.

관련한·관련하여를 관련이 있다의 활용형에서 제거하고 마칩니다·마쳤습니다·알립니다·알렸습니다 등 해당 표제의 대표 활용형을 추가했다. 추측 구성은 -(으)ㄴ·-는·-(으)ㄹ 형태로, 지속 조건은 -는·-(으)ㄴ·인 형태로 구별했다. frames의 한 원소에 세미콜론으로 이어 적었던 표현틀을 별도 배열 원소로 나눴다. 권한을 확인하다는 서술표현 범주로 맞췄으며 발생·증가·감소 조건의 불필요한 관계나를 지웠다.

KPL-0153은 근거 있는 불확실한 판단이라는 inference 뜻을 유지한다. 의견을 누그러뜨리는 완곡 기능은 이 뜻으로 승인하지 않으며 현재 미등록 용법으로 구별한다. LEX-SENSE-COURTESY-UNREGISTERED는 확인된 완곡 목적을 유지하는 작성자 사례이며 inference 의미를 승인하는 사례가 아니다.

첫 검토에 대응하면서 를이 모음으로 끝난다고 적었던 근거는 틀렸다. 를의 종성은 ㄹ이며 잘못된 설명을 명시적으로 철회했다. 조사가 결합된 예시를 나열하는 문장으로 바꿔 인용된 조사형에 다시 조사를 붙이는 설명을 없앴다. 이 수정은 corpus 독립성이나 한국어 독자 효과를 입증하는 결과가 아니다.

# 비공개 완료 보고서로 규약 입력을 비교한다

**이 기록은 중간본 `909dc9d`(실험 회차 r10)의 개발 평가다.** STE 대조군이 없으므로 현재 [평가 규칙](../README.md#ste-대조군을-필수로-포함한다)에서는 부분 진단이다. 현재 버전 v0.8.0의 원문·KP·STE 비교는 [세션 보고서 비교](../session-reports-20261015/README.md)를 따른다.

[run.py](run.py)는 비공개 원문 하나에 기존 r2 프로필과 새 실험 스킬을 각각 두 번 적용하는 개발용 러너다. 같은 원문·공통 요청·모델 설정을 사용하며, 생성 전 기준과 입력 해시를 고정한다. 이미 검토한 개발 사례를 사용하므로 결과를 보지 않은 홀드아웃 시험이 아니다.

공개 저장소에는 러너와 일반 절차만 둔다. 원문, 주장 목록, 원문별 판정 기준, 토큰 측정 자료, 요청·응답·출력과 평가 기록은 모두 비공개로 보관하며 커밋하거나 공개 예문에 복사하지 않는다. 공개 예문 6개의 과거 r2 결과를 이 실험 스킬의 통과 결과로 사용하지 않는다.

## 원문과 기준을 먼저 준비한다

저장소 루트에서 새 `output/<비공개 이름>` 하위 폴더를 사용하거나, 저장소 밖의 시스템 임시 디렉터리를 사용한다. 러너는 다른 저장소 내부 경로를 거부하고 기존 실험 기록을 덮어쓰지 않는다. `output/`의 Git 제외 여부를 확인하며, 제외 설정은 자료의 외부 공유를 막는 접근 제어가 아니다.

생성 전에 다음 파일을 비공개 실험 폴더에 준비한다.

- `source.md`에는 수정하지 않은 원문을 둔다.
- `claim-ledger.json`에는 원문의 독립 주장, 조건·수치·시간·행위자·의무 강도, 식별자와 출처의 대응을 기록한다.
- `criteria.json`에는 의미 보존과 구조 기준을 고정한다.
- `token-budget.json`에는 전체 스킬 해시, 규약 토큰 계수, 원문 토큰 계수와 실제 최소 요청의 증거를 기록한다.

의미 검사는 원문에서 출력으로, 출력에서 원문으로 양방향 대조한다. 원문에서 확인하지 못한 사실은 확인된 사실로 바꾸지 않는다. 원문 자체의 미검증 주장이나 충돌은 유지하고, 검토자의 감사 주석은 변환 출력과 분리한다.

구조 검사는 완료 결과와 사용에 필요한 운영·노출 조건을 기능·설계 상세보다 앞에 배치했는지 확인한다. 독립적으로 비교할 속성은 별도 항목·행·표의 셀로 찾을 수 있어야 한다. 선행 조건, 실제 순서, 선택적 보조 수단과 사후 조치를 한 필수 절차로 섞지 않는다. 의미 보존만으로 구조 검사를 통과하지 않는다.

## 규약과 공통 요청문의 토큰을 측정한다

**현재 작업은 사용자가 토큰 상한을 해제한 정책에 따라 품질을 우선하며, 토큰 수는 계속 측정한다.** 러너의 `core_prompt()`로 만드는 후보 스킬 전체와 공통 요청문을 로컬 계수기로 측정하고, 원문은 `source_tokens`에 따로 기록한다. 원문까지 포함한 실제 생성 요청의 `usage.input_tokens`도 보존한다.

러너는 기존 실험과의 호환성을 위해 기본 상한을 6,000으로 유지한다. 새 실험에서 상한을 해제하려면 `prepare --core-token-ceiling none`을 명시하고 `token-budget.json`의 `ceiling`을 JSON `null`로 기록한다. 상한 해제는 로컬 계수·원문 계수·실제 최소 요청의 사용량 측정을 생략하지 않는다. 과거 6,000토큰 정책으로 동결한 실험은 그 상한을 계속 적용한다.

`probe`는 별도 CLI 하위 명령이 아니다. `probe_request()`로 원문 없는 최소 요청을 만들고 실제 응답을 보관하는 사전 단계다. 전체 스킬의 메타데이터를 포함하며, 짧게 발췌한 규칙으로 계수하지 않는다.

아래 예시는 비공개 파일 이름만 사용한다. 원문·판정 기준은 앞 단계에서 준비하며, 로컬 OpenCodex 경로가 설정된 환경에서 실행한다.

```sh
export KP_STUDY_DIR=output/private-study
export KP_CANDIDATE=skills/korean-protocol/SKILL.md
python3 - <<'PY'
import importlib.util
import os
from pathlib import Path

spec = importlib.util.spec_from_file_location('study', 'evaluation/field-report-20261015/run.py')
runner = importlib.util.module_from_spec(spec)
spec.loader.exec_module(runner)
study = runner.validate_study_dir(Path(os.environ['KP_STUDY_DIR']))
probe = study / 'token-probe'
probe.mkdir(mode=0o700)
request = runner.probe_request(Path(os.environ['KP_CANDIDATE']).read_bytes(),
                               'anthropic/claude-opus-5-5', 'medium')
runner.write(probe / 'request.json', request)
with (probe / 'response.raw').open('xb') as raw:
    runner.transfer(runner.frozen.old.ENDPOINT, request, raw, {}, 600)
PY
```

이 단계는 실제 모델 요청 한 건을 보낸다. 요청 모델은 **Opus 5.5의 `anthropic/claude-opus-5-5`**, 요청 추론 강도는 **`medium`**으로 기록한다. 반환 모델 식별자가 다르거나 반환 강도가 다른 값이면 거부한다. 응답에 강도 필드가 없으면 `requested_effort: medium`, `returned_effort: null`, `effort_verification: unverified`로 구분하며 실제 medium 수행을 검증했다고 쓰지 않는다. 응답에 표시된 모델명도 상위 제공자의 실제 실행 모델을 독립적으로 증명하지 않는다.

`token-budget.json`은 다음 필드를 사용한다. 계수와 해시는 실제 파일과 실제 응답에서 산출하며 예시 값을 실측값으로 채우지 않는다.

| 필드 | 기록할 값 |
| --- | --- |
| `profile_sha256` | 후보 스킬 전체 바이트의 SHA-256을 기록한다. |
| `ceiling` | 상한 없는 새 실험은 JSON `null`을 기록하고 `prepare --core-token-ceiling none`을 명시한다. 기본·기존 정책은 `6000`을 사용한다. |
| `counters` | 계수기 이름별 `core_prompt()` 토큰 수를 기록한다. 값은 음수가 아닌 정수여야 하며, 상한이 있는 정책에서만 상한을 적용한다. |
| `source_tokens` | 계수기 이름별 원문 토큰 수를 별도로 기록한다. |
| `model_probe.profile_sha256` | 같은 후보 스킬 해시를 기록한다. |
| `model_probe.model_requested`, `effort` | 각각 요청 모델과 요청 강도를 기록한다. |
| `model_probe.request_file`, `response_file` | 실험 폴더 안의 실제 최소 요청·원시 응답 상대 경로를 기록한다. |
| `model_probe.request_sha256`, `response_sha256` | 해당 두 파일의 해시를 기록한다. |

러너는 최소 요청 바이트를 다시 구성해 대조하고 실제 응답의 `usage.input_tokens`를 확인한다. 상한 없는 정책에서도 이 값은 음수가 아닌 정수로 존재해야 한다. 6,000토큰 정책에서는 로컬 규약 계수와 실제 최소 요청 사용량이 모두 6,000 이내여야 한다.

## 입력을 고정하고 한 번 실행한다

```sh
python3 evaluation/field-report-20261015/run.py prepare \
  --study-dir "$KP_STUDY_DIR" --candidate "$KP_CANDIDATE" \
  --model anthropic/claude-opus-5-5 --effort medium \
  --core-token-ceiling none
python3 evaluation/field-report-20261015/run.py run \
  --study-dir "$KP_STUDY_DIR"
```

`prepare`는 원문·기준·주장 목록·토큰 증거·두 규약과 러너 해시 및 토큰 정책을 고정하고 요청 네 건을 만든다. 위 예시는 `token-budget.json`의 `ceiling: null`을 요구하며, plan에 `core_token_ceiling: null`과 `core_token_policy: {"mode": "measured-only", "ceiling": null}`을 기록한다. 옵션을 생략하거나 `--core-token-ceiling 6000`을 지정하면 기본 상한 6,000을 적용한다.

이 명령은 생성 요청을 보내지 않으며, 사전 최소 요청 증거가 이미 있어야 한다. `baseline`은 고정된 r2 프로필이고 `candidate`는 전달한 전체 스킬이다.

`run`은 각 조건 두 번씩 총 네 건을 보내며 최대 동시 요청은 두 건이다. 각 요청에는 원문 하나와 규약 하나 및 같은 공통 요청만 넣으며, 판정 기준·주장 목록·이전 답안·대화 이력은 넣지 않는다. 도구를 제공하지 않고 `store: false`로 요청하지만, 이 설정을 전체 중계 경로의 무보관 증명으로 사용하지 않는다.

요청별 전송 제한은 총 600초이며 자동 재시도는 하지 않는다. 실패·중단·식별자 불일치의 원시 응답과 가능한 종료 텍스트도 남긴다. 실패 기록을 성공 출력으로 교체하거나 같은 폴더에서 다시 생성하지 않는다. 새 실행은 별도 폴더와 실행 기록으로 구분한다.

## 원시 출력을 바꾸지 않고 검증한다

```sh
python3 evaluation/field-report-20261015/run.py verify \
  --study-dir "$KP_STUDY_DIR"
```

`verify`는 네트워크 없이 고정 입력·요청·응답·출력·사용량의 해시와 대응을 확인하고, plan에 동결한 토큰 정책을 적용한다. `run`과 `verify`는 `--core-token-ceiling`을 받지 않으므로 실행·검증 시점에 상한을 바꿀 수 없다. 상한 변경은 새 폴더에서 새 정책으로 `prepare`할 때 지정한다.

완료 응답의 `output_text`는 앞뒤 공백·줄바꿈까지 그대로 보관한다. 의미 오류가 있어도 교정·재정렬·요약하지 않으며, 후속 수정본은 원시 출력과 별개로 기록한다. 러너를 바꾼 뒤 과거 기록을 검증할 때의 `--archived-runner`는 보관한 러너 바이트의 해시 대조 전용이며 과거 코드를 실행하거나 새 요청을 보내지 않는다.

전송·해시 검증 통과와 의미·구조 통과는 별개다. 검토자는 주장별 출력 위치, 추가·누락·변경된 의미, 구조 조건별 판정과 근거를 따로 기록한다. 문자 수는 raw·가시 문자·공백·Markdown 및 링크 차이를 구분하며, 규약 토큰 예산이나 의미 보존 판정을 대신하지 않는다.

이 러너의 비교는 **규약 텍스트를 직접 넣은 실험**이다. 설치된 스킬의 발견·실제 로딩을 증명하지 않는다. 아래의 Codex 파일 읽기 검사는 별도 실행이며, 수동 설치와 호출은 [실험 스킬 안내](../../docs/distribution/on-demand-skill.md)를 따른다.

## 보완 후보의 검증 범위를 밝힌다

2026-10-15의 10차 후보는 아래 개발 검사를 통과했다. 원문과 의미·구조 기준을 유지하면서 규약을 보완했으며, 생성된 출력을 교정하지 않았다. 7차부터 규약 토큰 상한만 해제했고 의미·구조 기준은 완화하지 않았다.

| 검사 | 결과 |
| --- | --- |
| 같은 실전 보고서를 두 번 변환했다. | 두 출력 모두 독립 주장 129개·구조 기준 13개·필수 식별자를 보존했다. |
| 고정 r2 규약도 같은 보고서로 두 번 실행했다. | 구조 기준은 각각 3/13·5/13을 충족했다. 두 번째 출력은 원문에 없는 인과도 추가했다. |
| 기존 짧은 예문 6개를 다시 실행했다. | 의미와 조건별 목록화·핵심 판단 배치 등 사례별 구조 검사를 모두 통과했다. |
| 별도로 작성한 합성 사례 4개를 두 번씩 실행했다. | 8개 출력 모두 의미·구조 검사를 통과했다. 네 원문은 총 104개 주장과 19개 구조 기준을 포함한다. |
| 임시 Codex CLI 프로젝트에서 스킬을 호출했다. | 전체 규약·원문을 최종 답변 전에 읽은 기록을 확인했다. 이 별도 출력은 주장 53개·구조 기준 7개를 통과했다. |

보완한 규약은 종료·만료·중단 조건을 결과 바로 뒤에 두고, 일반 주장과 특정 기능 주장을 각각 보존한다. 대상·조건별 규칙과 입력·표시 항목을 나눈다. 시간 조건을 행동 의무로 바꾸거나, 실행 가능을 권한으로 해석하거나, 시험 방법을 성공 결과로 강화하지 않도록 명시했다.

보고서가 짧아진 것은 아니다. 원문은 원시 3,242자·가시 2,716자이고, 두 후보 출력은 원시 3,817자·3,715자와 가시 3,095자·3,039자였다. 원시 분량은 17.7%·14.6% 늘었다. 독립 속성의 이름과 줄바꿈이 늘어난 결과이며, 분량 감소나 실제 독해 속도 개선을 입증한 수치로 사용하지 않는다. 가시 문자는 원문과 출력에 같은 Markdown 부분집합 투영을 적용해 계산했다.

10차의 전체 스킬과 공통 요청문은 실제 최소 요청에서 **10,842토큰**이었다. 같은 텍스트는 `o200k_base` 6,241토큰, `cl100k_base` 9,561토큰이었다. 긴 원문을 포함한 실제 후보 요청은 **13,785토큰**이었다. 이 값은 Codex의 다른 지침·도구·대화 이력을 포함한 전체 컨텍스트 크기가 아니다. 후보의 SHA-256은 다음과 같다.

```text
bff3435ffce9d7c6e7c3906cf65b8e89a170c1365a98ecb614add83d97ee16a9
```

모든 생성은 **Opus 5.5·medium을 요청**했다. 직접 입력 실험의 반환 모델명은 일치했지만 추론 강도는 반환되지 않았다. 따라서 실제 medium 수행을 확인했다고 말하지 않는다. Codex 파일 읽기 검사는 요청 설정과 읽기 기록을 확인했으며, 상위 제공자의 모델·강도를 독립적으로 인증하지 않았다.

Codex 검사는 사용자 설정을 읽지 않는 임시 프로젝트에서 수행했다. 첫 시도는 규약 앞부분과 크기만 확인해 전체 읽기를 입증하지 못했다. 그 기록을 보존한 뒤, 전체 본문 읽기를 명시한 별도 요청을 실행했다. 이전 출력이나 의미 검토 피드백은 새 요청에 넣지 않았다. 스킬·원문 전체와 명령 출력의 해시가 일치했고, 최종 출력도 도구 기록과 일치했다. 이 검사는 다른 호스트의 자동 발견이나 명시적 읽기 요청 없이 적용되는 동작을 보장하지 않는다.

10차까지의 이전 실패와 원시 출력도 보존한다. 추가 사례는 처음 만들 때 규약·출력을 보지 않고 기준을 고정했지만, 여러 번 보완에 사용했으므로 현재는 개발 회귀 사례다. 이번 통과를 새로운 문서 전체의 성공률이나 독자의 재독 감소로 일반화하지 않는다. 원문이 보고한 실제 장치 동작·권한·견적·미래 실행은 별도로 사실 확인하지 않았다. 정식 0.7 서명 배포본과 사용자 전역 설치도 교체하지 않았다.

## 과거 후보의 판정을 구분한다

이 절의 수치와 판정은 아래 해시의 과거 후보에만 해당하며, 현재 후보의 결과로 사용하지 않는다. 당시 후보는 6,000토큰 상한으로 평가했다.

해당 스킬 전체와 공통 호출문은 Opus 경로의 원문 없는 최소 요청에서 **5,951토큰**으로 계측했다. 같은 텍스트의 `o200k_base`는 3,432토큰, `cl100k_base`는 5,255토큰이다. 이 수치는 호스트의 다른 지침·이력·원문을 포함한 전체 컨텍스트 상한이 아니다. 후보 해시는 아래와 같다.

```text
825272c90a0e102602163d15cdae5e1b2d128d3abd7ceae3c13a222e52e6f28f
```

기존 짧은 원문 6개는 해당 과거 후보의 의미·구조 검토에서 모두 통과했다. 그러나 긴 실전 보고서의 두 반복 출력은 모두 전체 기준을 통과하지 못했다. 구조 검사는 각각 12/13이었으며, 운영 종료 조건의 앞쪽 배치와 일반 주장·특정 기능 설명의 범위 보존에 문제가 남았다.

해당 과거 후보는 반복 관찰한 개발 사례로 보완했다. 새로운 문서에 대한 일반화, 독자의 재독 감소, 설치된 스킬의 실제 로딩은 검증하지 않았다. 코드 테스트와 CI 통과는 생성된 보고서의 의미·구조 합격을 뜻하지 않는다. 민감한 원문과 미가공 출력, 상세 판정은 비공개 로컬 기록으로 보존하며 공개 저장소에 넣지 않는다.

스킬화는 필요한 작업에서 규약을 읽게 하는 적용 방식이다. 실제 출력의 준수를 보장하는 장치로 간주하지 않으며, 정식 0.7의 상시 지침·서명 배포본을 이 후보로 바꾸지 않는다.

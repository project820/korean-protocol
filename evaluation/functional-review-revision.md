# 기능 설계 검토의 재검토 기록

Opus가 발견한 의미 변경·사례 구성 결함을 수정 전후 자료와 대조한 뒤 49개 기능 통과와 4개 부분 대응을 유지했다. 이 결과는 2026년 10월 12일의 기능 설계 검토이며 실제 LLM 생성·출력 평가나 독자 실험 결과가 아니다.

## 1. 이전 검토의 부족한 범위를 공개한다

초기 기능 검토는 규칙의 요구사항·조건·예외와 대응 사례를 대조했지만, 작성자 `-N` 사례 전체를 입력·문맥만으로 재구성할 수 있는지 충분히 검사하지 않았다. 그 결과 외부 정상 예문의 정답을 전제하는 사례와 조건을 확정 진술로 바꾼 정상 예문의 결함을 놓쳤다. 초기 통과 수만으로 작성자 사례 집합 전체의 의미 적합성을 보장할 수 없었다.

이번 재검토에서는 수정 전 기준 파일과 수정 후 파일의 필드 차이를 확인하고, 수정된 `-N` 72개 전체의 문맥·실제 원문·편집 후보·기대 출력을 읽었다. 규칙의 요구사항 또는 예문이 바뀐 11개 규칙을 다시 대조했으며, 원본 53개 기능의 규칙 참조와 사례 참조를 재검사했다. 이전 해시는 현재 검토 증거의 `revision.previous_hashes`에 보존한다.

## 2. 발견된 결함별로 수정과 판정을 기록한다

| --- | --- | --- |
| PROC-006은 공유된 기준에서 수정과 유지를 동시에 기대했다. | 정상 예문의 E1 연결은 독자에게 미공유된 상태로 바뀌었고 M-006은 공유 상태를 유지한다. | `FC-REV-SHARED`, `FC-REV-UNSHARED`, `FC-REV-NOCRITERION`은 같은 입력에서 각각 유지·수정·확인을 구분한다. |

| SYN-006은 이미 명확한 첨가 연결의 분리를 강제했다. | 정상 사례의 판정은 `keep`으로 바뀌었고 위반 이유는 미확인 인과관계를 추가했다고 바로잡았다. | `FC-REV-LINK`는 짧고 명확한 나열을 유지하고 인과로 바꾸는 대안을 거부한다. |
| 사례 이유의 반복 문구와 문구 오류가 판단을 흐렸다. | 작성자 `-R` 72개의 이유가 실제 변경 항목을 설명하도록 바뀌었고 VER-001·SYN-006·WRD-008의 지적 문구가 수정됐다. | 이유 문구의 존재를 효과 입증으로 계산하지 않았으며 실제 조건·출력 차이를 별도로 대조했다. |

`-N`은 원문을 보존하는 편집 후보 교정 과제이며 후보 자체를 새 원문으로 승인하는 과제가 아니다. 수정된 사례에서는 원문에 있는 내용으로 후보의 오류를 복구하므로, 입력 후보와 출력이 다르다는 이유만으로 사실 창작이라고 판정하지 않는다. 반대로 명시 원문과 확인 문맥이 없으면 작성자 예문의 답을 가져와 보충할 수 없다.

## 3. 독립 사례도 다시 검토한다

기존 75개 사례에 회귀 사례 9개를 추가해 총 84개를 기록했다. 사용자 지정 공통 문장인 `FC-7-3`은 `independent: false`로 남기고 원본 기능별 검토의 `case_ids`에서 제외했다. 나머지 83개 입력은 수정된 작성자 사례의 입력과 정확히 일치하지 않으며, 작성자 사례 242개는 모두 `origin: author`로 분리한다.

독립 사례의 세 가지 적용 조건도 교정했다. `FC-3-3-U`는 관형형의 모호성을 검사 완료와 착수 이력의 차이로 구체화했다. `FC-4-3`은 짧은 두 조건의 나열을 무조건 목록으로 고치던 기대값 대신 독자가 비교해야 하는 네 분기를 사용한다. `FC-8-1`은 명확한 세미콜론의 일괄 수정 대신 조건 관계가 모호한 부호 나열을 사용한다.

`FC-REV-COND`의 허용 대안은 공통 조건 아래에 알림과 확인을 모두 둔다. 한 문장을 나눈 뒤 뒤 문장을 무조건 수행하는 것으로 해석할 여지를 줄이기 위해 이 구조를 선택했다. 조건 유지 검토는 원본의 행동 수나 짧아진 글자 수와 별도로 수행한다.

## 4. 앞선 예문 재검토 당시의 대상 버전과 검사를 기록한다

| 대상 파일은 다음과 같다. | 재검토한 SHA-256은 다음과 같다. |
| --- | --- |
| `specification/rules.json`을 검토했다. | `5d8db818c0a50e4249fae2a4bd69a65418b29c3ff23ba20d4e468b0106d10ae0` |
| `examples/rule-cases.json`을 검토했다. | `aa589b56a0c0896cfb8f695abad9a5fed91e4a33f42bc5aedca8f1ca0c26a397` |
| `docs/spec/korean-rules.md`를 검토했다. | `10aa7cd07fab89505fdbdc95e3948c721655f8ca7a0378b73deac0286d1ee9ae` |

독립 사례 파일의 현재 해시는 [functional-review.json](functional-review.json)의 `independent_cases_sha256`에 묶었다. 이전 파일의 해시와 현재 파일의 해시를 바꿔 넣는 것만으로 통과를 승계하지 않았으며, 변경 규칙·사례와 추가 회귀의 대조 결과를 각 영향 기능의 `rationale`에 반영했다. 행동 기준의 공유 여부를 직접 검증하는 9.2에는 실제 기여 규칙 `KP-PROC-006`을 추가했다.

Python 검사에서 `-N` 72개 모두 실제 원문·확인 문맥·후보 교정 과제를 포함했고, 숨은 정상 예문 참조는 남지 않았다. 같은 입력·문맥에 서로 다른 기대 출력 또는 판정이 붙은 충돌은 없었다. 별도 검사에서 작성자·독립 사례 ID, 원본 53개 기능 집합, 규칙 전방 참조, 검토·사례 참조, 네 파일 해시와 유지·수정·확인의 불변 조건을 확인했다.

기능 설계 대응은 49/53이며 부분 대응은 1.1·5.1·6.3·6.6이다. 1.1은 폐쇄 승인 어휘 통제를 완전히 구현하지 않고, 나머지 세 항목은 강제 길이 상한 대신 수동 검토 신호를 사용한다. 이 차이는 수정된 예문의 품질과 별개이므로 부분 대응을 유지한다.

현재 결과에는 실제 LLM 생성 실행, 사람의 독해 성능, 분야별 어휘 충족률, 실제 환경의 설치·업데이트 검증이 포함되지 않는다. 해당 관문은 별도 증거가 있어야 통과할 수 있다.

## 5. 최종 예문 잔여 수정을 확인한다

언어 재검토 뒤 WRD-002·PROC-006·PROC-007의 예문을 다시 대조했다. WRD-002의 원문은 “서버 공개”를 사용하므로 문맥에 정의된 배포와 직접 연결되며, 의미가 정해지지 않은 “서버 저장”을 배포로 추정하지 않는다. PROC-006의 위반 이유는 “원문과 문맥에 없는 복구 동작”으로 한정해 제공되지 않은 E1 절차의 내용을 단정하지 않는다. PROC-007은 필수 조치를 본문으로 옮기면서 붙였던 첫 단계 번호를 제거했다.

각 수정은 작성자 R/N 사례와 상세 문서에 함께 반영됐다. 직전 재검토에서 읽은 변경 필드를 포함한 규범 기준선과 비교했을 때 72개 규칙의 requirement·conditions·exceptions는 바뀌지 않았다. 독립 사례 `FC-1-3`, `FC-REV-SHARED`, `FC-REV-UNSHARED`, `FC-REV-NOCRITERION`, `FC-5-5`, `FC-5-5-L`의 판정은 현재 규칙과 계속 일치한다. 특히 두 주석 사례의 허용 대안에는 임의의 첫 단계 번호가 없으므로 사례를 수정하지 않았다.

SYN-006의 R은 정상 판정 사례이므로 이미 정확한 첨가 연결을 `keep`으로 유지한다. 같은 규칙의 N에는 원문에 없는 인과관계를 추가한 후보가 있어 `revise`가 필요하다. 상세 문서는 이 차이를 명시하며 `FC-REV-LINK`도 명확한 첨가 연결을 그대로 두므로, 정상 사례를 반드시 수정 사례로 바꾸라는 제안은 채택하지 않는다.

현재 검토 해시는 제4절의 최종 파일로 갱신했고 직전 해시는 `functional-review.json`의 `revision.final_example_refinement.previous_hashes`에 보존했다. 추가 사례 변경 없이 49개 통과·4개 부분 대응과 독립 83개·공통 회귀 1개를 유지한다.

## 6. 두 규칙 정교화 뒤 기능 설계 판정을 다시 확인한다

`refinement_coverage / GPT-6 Astra high`는 두 규칙 작성에 참여하지 않은 별도 검토자로서 2026년 10월 12일 기준본과 현행 자료를 대조했다. 현행 기능 설계 판정은 49개 통과와 4개 부분 대응이며, 이 절의 해시가 정교화 뒤 검토 대상을 고정한다. 제1~5절의 검토 범위·242개 작성자 사례 수·해시는 앞선 예문 재검토의 이력으로 보존한다.

기준본 `evaluation/baselines/20261012-before-rule-and-lexicon-refinement/manifest.json`의 14개 파일 해시는 보존 파일과 모두 일치했다. 전체 규칙 레코드를 비교한 결과 `KP-VER-005`와 `KP-KO-007`만 바뀌었고 나머지 70개는 모든 필드가 동일했다. 기존 작성자 사례 242개는 순서와 모든 필드가 동일하며, 신규 14개를 더한 현행 256개 모두 `origin: author`이다. 독립 사례 파일의 해시는 이전 검토에 고정된 값과 같으며 83개 독립 입력과 공통 회귀 1개를 유지한다.

선정 대응표에서 두 규칙의 영향을 받는 기능은 3.4와 3.6이다. `KP-VER-005`의 참고 범위에는 3.5도 있지만 3.5의 실제 선정 규칙은 변경되지 않은 `KP-VER-006`과 `KP-SYN-009`이므로 이 개정에 새 기능 점수를 주지 않는다. 대응표 전체도 기준본과 바이트 단위로 같으며 나머지 51개 기능의 선정 규칙과 기존 사례는 변하지 않았다.

3.4는 기존 시험·준비·비의도성·변화 보존과 의미 없는 중복만 줄이는 예외를 유지한다. 새 상세 절차는 `-고 있다`의 동사 뜻과 문맥을 읽어 진행과 결과 유지를 구별하며 모든 표현을 `-는 중`으로 바꾸지 않는다. 기존 독립 `FC-3-4`의 가능성 유지와 `FC-REV-CANDIDATE`의 허락 복구는 결합 규칙 `KP-VER-003·007·008` 및 정교화한 두 규칙과 충돌하지 않는다. 기존 독립 사례 두 개의 허용·거부 대안을 다시 대조해 3.4 통과를 유지했다.

3.6은 `KP-VER-002`의 책임 명시 조건과 상태 중심 예외를 계속 적용한다. 정교화한 `KP-KO-007`은 일반 피동에서도 행위자와 영향을 받은 대상을 보존하며 사동주를 직접 실행자로 치환하지 않는다. 기존 독립 `FC-3-6`은 알려지지 않은 행위자를 만들지 않고 상태를 유지하며, `FC-3-6-A`는 이미 확인된 책임자를 명시한다. 두 사례와 새 상세 절차를 다시 대조해 3.6 통과를 유지했다.

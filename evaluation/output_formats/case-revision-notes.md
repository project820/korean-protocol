# 평가 입력의 모호함을 구분한다

run-02의 D07은 ‘a는 1000~5000원, n은 1~12주의 정수다’라고 적었다. 검토자가 a의 정수 여부를 미해결로 판정했다. 해당 원문과 출력·판정은 run-02의 고정 기록에 보존했다. 다음 실행의 개발 입력에서는 a와 n의 정수 조건을 각각 명시한다. 이 변경으로 과거 후보의 의미 보존 판정을 통과로 바꾸지 않는다.

run-03은 후보만 고정했고 생성하지 않았다. run-03용 새 평가 자료는 cases-run-03에 보존하며 run-04의 새 평가로 재사용하지 않는다.

run-05는 D07 단회 생성 36건과 익명 검토 12건을 완료했다. 후보 형식 실패 2건과 의미 미해결 1건을 유지한다. 사용자는 이후 세 비교군에 같은 검사 도구와 자체 수정 기회를 제공하는 별도 평가를 선택했다. run-05의 원문은 cases-run-05에 보존한다.

run-06은 검사 도구를 포함한 후보를 고정하고 새 평가 원문을 작성했으나 모델 출력을 생성하지 않았다. 독립 코드 검토에서 진단 도구의 JSON 출력과 외부 의존성 탐지 결함을 발견했다. 해당 후보와 원문은 보존하며, 원문은 cases-run-06에서 확인한다. 수정 후보는 새로 고정하고 새 평가 원문을 작성한다.

run-07은 수정한 검사 도구를 포함한 후보와 별도 평가 원문을 고정했다. D07의 도구 보조 작업 36건 중 35건은 진단을 통과했다. 입력 제어가 없는 HTML 1건을 평가기가 도구 인식 실패로 분류해 미완료로 남겼다. 해당 판정과 모든 시도·진단을 유지한다.

run-08은 이 분류 오류를 수정한 평가기를 별도로 고정했다. 스킬 후보·패키지·평가 원문은 run-07과 바이트가 같으며, 기존 후보 고정 시각을 그대로 유지한다. run-07에서 새 평가 원문에 대한 모델 출력은 생성하거나 판정하지 않았다. 재사용 근거는 run-08/snapshot-reuse.json에 기록한다. 후보 변경 뒤 원문을 새로 작성해야 하는 규칙은 완화하지 않았다.

run-08은 개발 출력 246건과 유효 익명 검토 40건을 확보한 뒤 중단했다. 후보 의미 판정은 40건 모두 통과했지만, 형식은 38건 통과·2건 미해결이었다. L1의 ‘일반 텍스트’ 계약에 Markdown 제목·강조의 허용 범위가 불분명했고, 한 검토는 요구되지 않은 문자 그대로의 ‘주의’ 표지를 판단 조건으로 삼았다. 원자료·요청·실제 출력에 대한 독립 검토에서 이 두 불확실성을 평가 계약의 모호함으로 확인했다.

run-09는 모든 비교군에 같은 L1 허용 범위와 경고 판정 기준을 명시한다. 개별 요청의 명시적 제한은 계속 우선한다. 두 사례에 대한 별도 진단은 원문·세 비교군을 함께 사용해 새 판정 기준을 확인했으며, run-08의 판정을 고치거나 현재 품질 근거로 승격하지 않았다. run-09는 세 비교군을 모두 새로 생성한다. 후보와 아직 출력하지 않은 평가 원문은 그대로 보존하고 재사용 근거를 snapshot-reuse.json에 기록한다.

## run-09의 중단과 후속 기준을 구분한다

run-09는 개발 출력 280건과 익명 검토 60건을 확보한 뒤 중단했다. 최종 검토 기록(로컬 기록 `output/kp-output-formats-20261020/run-09/review-summaries/final-review-status.json`)은 유효 검토 59건과 D01의 부정확한 인용으로 인한 무효 검토 1건을 남긴다. 후보의 의미는 유효 검토 59건 모두 통과했고 형식은 57건 통과·D06 2건 미해결이었다. 이 기록은 비교 완료나 품질 향상을 입증하지 않는다.

D06의 작업은 특정인에게 귀속할 근거가 없는 값을 ‘별도로 둬라’고 요청했다. 두 검토는 같은 표의 독립된 행이 이 요구를 충족하는지 미해결로 남겼다. 다음 비교의 [공통 형식 기준](study.py)은 원문·요청에 별도 표나 열의 명시적 요구가 없으면 대상·출처·상태가 분명하고 공통 귀속을 만들지 않는 독립된 행·문단·목록 항목을 허용한다. 이 기준은 구분할 수 없는 배치를 통과시키지 않으며 분리 방식의 선호는 명료성에서 비교한다.

D08의 이전 요청은 초기 입력값이 유효 범위에 있어야 한다고 명시하지 않았으므로 해당 초기 유효 입력 검사에는 요청 근거가 부족했다. D07·D08은 초기화 기능을 요구했지만 무엇을 복원하는지 명확하지 않았다. 두 작업 요청에 ‘초기 입력값은 허용 범위 안에서 정하고, 초기화하면 처음 표시한 입력값과 계산 결과로 복원하라.’를 추가했다. 원문·수식·입력 범위는 유지하고 데이터셋과 오라클 해시를 갱신했다.

E07~E09는 원문·요청에 초기값·시작 상태와 초기화 동작이 명시돼 있어 바꾸지 않았다. 이 개정은 개발 작업의 검사 근거를 명시하는 변경이며 미사용 평가 원문이나 과거 판정을 수정하지 않는다.

D09의 원문은 대기·확인 중·완료 사이의 전이를 정했지만 설명 도구의 시작 상태는 정하지 않았다. 이전 오라클의 시작 상태 ‘대기’에는 당시 작업 요청의 근거가 없었다. 수정한 [개발 작업 요청](development.json)은 도구의 시작 상태를 ‘대기’로 명시하고 모든 상태에서 가능한 도구 초기화를 별도로 요구한다. 원문의 초기화는 완료→대기 전이로 유지하고 도구 초기화를 원문의 허용 전이에 추가하지 않는다.

D09의 원문 바이트와 상태 전이는 바꾸지 않았다. 도구 전체 초기화와 원문 초기화를 혼동한 제어 선택, 장식용 상태명을 현재 상태로 읽은 브라우저 결함은 수정한 뒤 run-10에서 별도로 고정했다. 수정한 작업 요청·원문 해시·오라클·검사기는 세 비교군에 같은 조건으로 적용했다.

새 `exact-quote-repair/v1`은 스키마와 판단 구조가 유효한 검토에서 부정확한 인용 문자열만 최대 2회 정정한다. 판정·이유·기존 유효 인용·순서는 잠그며 유효한 실패·미해결 판정을 재시도하지 않는다. 최초·정정 검토는 `attempts/0..2/`와 `selection.json`으로 보존하고 `review_result`로 다시 검증한다. 이 절차로 run-09의 무효 검토나 과거 판정을 고치지 않는다.

run-10은 세 비교군을 새로 생성·검토한 별도 비교였으며 후보는 run-07의 r7과 같은 바이트를 유지했다. 새 평가 원문은 출력 생성·판정에 사용하지 않았다. 기존 사용자 설치 v0.9.0은 유지하며 품질 비교는 미완료다.

run-10은 D06 후보의 전언 귀속 범위 미해결과 D09 수정 응답의 서버 연결 종료로 중단했다. 과거 판정·실패를 그대로 보존한다. r8은 표 분해 전 수식 범위를 확인하는 일반 지침과 다른 가상 의미 경계 사례를 추가한 별도 후보이며, 코어 문장은 바꾸지 않았다. run-10의 입력 파일은 cases-run-10에 보존했다.

run-11의 r8 후보 고정 기록(로컬 기록 `output/kp-output-formats-20261020/run-11/candidate-freeze.json`)은 후보 ID `4f9beb2d1e6bd3b68368fe8a182d78131f63234e1bd95fa49417f131508b2b8a`를 보존한다. 새 평가 원문 12개는 이 고정 뒤 작성했으며 정식 모델 생성·검토는 아직 시작하지 않았다. 사용자는 기본 KP와 L1~L4 스킬 구조를 먼저 로컬에서 쓰도록 지시했다. 이에 따라 전송 오류 복구의 선택 질문·정책 확장 개발·평가 확대를 중단하고 정식 계획은 새로 고정하지 않았다.

기존 설치의 백업·설치 기록·명시 호출 설정을 보존하는 사용자 범위 갱신을 우선한다. 이 로컬 사용은 run-10의 실패·미해결 판정이나 r8 준비 기록을 바꾸지 않는다. 정식 배포 설치기의 품질 게이트도 유지한다. 정식 비교는 별도 후속 범위로 남기며 새 비교를 시작한다고 약속하지 않는다.

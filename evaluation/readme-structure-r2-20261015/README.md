# 6,000토큰 이내 압축 규약을 비교한다

**2차 압축 후보는 같은 원문 6개에서 의미·구조 기준을 모두 통과했다.** 기존 0.7 프로필만 넣은 재실행본은 4개가 통과했다. 후보의 실제 전체 입력은 **최대 5,888토큰**이었다. 독자의 이해 시간이나 재독 횟수는 측정하지 않았다.

## 다른 프로젝트에서 임시로 적용한다

다른 프로젝트의 LLM 대화에 아래 요청문을 붙여 넣는다. **이 파일은 0.7을 바탕으로 만든 실험 후보다.** 정식 0.7 배포 파일과 설치 설정은 바꾸지 않았다.

```text
이 대화에서만 Korean Protocol 압축 후보를 임시 적용해.

아래 규약 파일을 끝까지 읽고 이후 한국어 답변에 적용해.
https://raw.githubusercontent.com/project820/korean-protocol/main/evaluation/readme-structure-r2-20261015/candidate-profile.md

전역 설정, 프로젝트 파일, 설치·자동 갱신 설정은 변경하지 마.
규약과 사전 전체를 중복해서 읽지 말고, 사전은 필요한 항목만 조회해.
파일을 읽지 못하면 적용했다고 말하지 말고 실패를 알려줘.
다 읽었으면 파일명과 첫 번째 절 제목을 알려줘.
```

URL을 읽지 못하는 환경에서는 [규약 파일](candidate-profile.md)을 내려받아 대화에 첨부하고 “첨부한 규약을 이 대화에서만 적용해”라고 요청한다. 파일 읽기 확인은 이후 답변이 모든 규칙을 지킨다는 보증이 아니므로 실제 답변도 확인한다.

중단하려면 “이 대화에서 임시 적용한 Korean Protocol을 해제해”라고 말한다. 새 대화에는 이 임시 요청이 자동으로 이어지지 않는다. 해제 요청은 이미 입력된 규약을 컨텍스트에서 삭제하지 않는다.

## 규약과 판정 기준을 보완했다

기존 출력에서 3번은 처리 순서를 번호로 나누지 않았고, 5번은 최종 배포 제한보다 실행 성공을 먼저 썼다. 프로필을 실제 입력한 기록과 출력 해시를 확인했으므로 파일 누락으로 판정하지 않았다. 모델 내부에서 어떤 지시를 우선했는지는 확인할 수 없다.

기존 규약에는 순차 번호 규칙이 있었지만 단계별 조건이 이어지는 흐름의 적용 기준이 분명하지 않았다. “이미 명확한 문장은 유지한다”는 예외와 구조 변경의 우선순위도 정리되지 않았다. 보고문을 다시 쓸 때 여러 결과 중 무엇을 먼저 놓을지 명시하는 규칙과 구조 합격 검사가 필요했다.

압축 후보에는 다음 기준을 넣었다.

1. **의미와 구조를 모두 통과해야 한다.** 표현 교정과 구조 재작성을 구분한다.
2. **실제 선후가 있는 여러 단계를 번호로 나눈다.** 동시에 수행하는 행동이나 단순 상태에 번호를 강제하지 않는다.
3. **공통 조건은 원문에서 적용 범위를 확인한 경우에만 제목으로 올린다.** 확인되지 않은 조건은 해당 단계에 남긴다.
4. **최종 사용·배포를 제한하는 결과를 보고 첫머리에 둔다.** 원문에 없는 실패 판정은 만들지 않는다.
5. **대상·선택지·기한을 분리한다.** 기본 기한과 대체 기한, 행동 주체와 자동 처리를 유지한다.

반복 지침을 묶고 드문 어휘 등록 판단은 필요할 때 관련 항목만 조회하게 했다. 상세 규칙 72개를 문장별로 동일하게 압축했다는 주장은 하지 않는다. [변경 범위](candidate-rules.json)와 [후보 전문](candidate-profile.md)을 함께 확인한다.

[1차 후보](../readme-structure-r1-20261015/README.md)는 3번 공통 조건의 범위가 불확실해 5/6만 통과했다. 2차에는 위 3번 규칙을 보완했다. 두 차수 모두 원출력을 수정하지 않았고, 같은 합격 기준을 사용했다.

## 입력 토큰을 측정했다

| 측정 대상 | KP 0.7 | 2차 압축 후보 |
| --- | ---: | ---: |
| 규약만 `o200k_base`로 계산했다. | 7,985 | 3,255 |
| 규약만 `cl100k_base`로 계산했다. | 12,076 | 5,042 |
| 규약과 최소 확인 요청을 Opus에 보냈다. | 13,350 | 5,611 |
| 원문·변환 지시까지 넣은 실제 요청 6개를 측정했다. | 13,495~13,627 | **5,756~5,888** |

실제 요청의 최대 입력은 같은 조건의 0.7보다 약 57% 줄었다. 입력 토큰에는 규약·원문·변환 지시가 포함되며 출력과 추론 토큰은 포함되지 않는다. 토크나이저별 수치를 분리했고 실제 응답의 `usage.input_tokens`로 6,000 한도를 검사했다. 출력은 한도를 넘더라도 보존하도록 실행기를 구성했다.

호스트의 시스템 지침, 이전 대화, 큰 원문, 추가 사전 조회는 입력을 더 사용한다. 따라서 **6,000은 이 후보의 기본 규약 예산이며 전체 세션 한도가 아니다.** 프롬프트 캐시는 컨텍스트에서 규약을 없애지 않는다. [공급자 문서](https://platform.claude.com/docs/en/build-with-claude/context-windows)도 캐시 토큰을 컨텍스트에 포함한다. 이 실험에는 로컬 추정치인 OpenCodex `count_tokens` 응답을 실제 공급자 측정으로 사용하지 않았다.

## 실제 출력을 비교한다

Opus 5.5·medium에서 원문별로 각 조건을 한 번씩 실행했다. 두 조건은 **프로필 하나만 다르고 원문·변환 지시가 같다.** 전체 사전, 기존 대화, 도구, 설명용 정답, 설치 지침 파일은 입력하지 않았다. 중계기와 공급자의 기본 지침은 이 격리 범위 밖이다. 모델 이름은 반환 메타데이터에서 확인했으며 공급자 내부 라우팅까지 독립 확인한 것은 아니다.

왼쪽은 원문, 가운데는 0.7 프로필만 넣은 재실행본, 오른쪽은 2차 압축 후보의 출력이다. 문장과 목록 번호는 교정하지 않았으며 제목·굵게 표시·줄바꿈만 표시한다. 원문 링크에서 공백을 포함한 원출력을 확인할 수 있다.

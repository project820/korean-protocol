# Korean Protocol

KP 기준의 작성·재작성·정리를 요청받은 작업에만 적용한다. 사용자가 지정한 범위, 장르, 문체, 형식이 이 규약보다 우선한다.

## 우선순위

1. 사용자 지침, 작업 범위, 지정 장르·높임·형식
2. 의미 보존: 사실, 양태, 범위, 주체, 출처
3. 문서 유형별 구조 배치
4. 간결하고 자연스러운 표현

의미와 구조를 각각 지킨다. 윤문으로 구조 개선을 대신하지 않고, 구조 변경으로 윤문을 대신하지 않는다.

## 요청 판별

- **표현 교정**: 구조, 순서, 문체를 유지하고 어색한 부분만 고친다. 명확한 문장은 두고, 명사화·번역투·겹친 피동은 같은 행동임이 확인될 때만 고친다.
- **구조 정리·재작성·새 글**: 문서 유형별 구조를 적용하고 이미 충족한 부분은 유지한다.
- **사실 정정·내용 변경**: 근거를 확인하는 별도 작업으로 다루고 바뀐 내용을 밝힌다.

맡긴 범위를 넘는 윤문은 하지 않는다. 실행에 필수이고 문맥으로 정할 수 없는 정보만 묻는다. 위임받지 않은 담당자를 배정하지 않고, '알아서'처럼 방법이 위임된 지시에 새 행동을 강제하지 않는다.

지정이 없으면 새 글은 높임 없이 쓴다. 설명·보고는 ~다, 번호 절차의 독자 행동은 ~한다, 지시는 ~하라, 금지는 ~하지 마라, 요청은 ~해 주기 바란다, 질문은 ~는가로 쓴다. 기존 글은 확립된 문체를 유지하고 독자나 장르만으로 높임을 추정하지 않는다. 사물에 붙은 높임은 없애되 실제 인물의 주체 높임, 인용, 지정 높임은 보존한다.

## 작성 전 정리와 작성 후 대조

작성 전에 원문의 주장, 역할, 의무, 조건, 시간, 불확실성, 보존 문자열을 정리한다. 작성 후 의미와 구조를 따로 원문과 양방향으로 대조해 누락·변경·추가를 고친다. 이 과정, 규칙 번호, 판정 문구는 출력하지 않는다.

## 의미 보존

- **진실성**: 사실, 추정, 가능성, 확인, 전언과 그 출처를 구별한다. 모호한 주장은 원문의 한정어를 유지하거나 인용한다. 원문이 말한 외부 사실을 편집자가 검증한 것처럼 쓰지 않는다.
- **양태**: 의무, 허락, 가능, 권고를 서로 바꾸지 않는다. '수 있다'를 확정으로, 허락을 명령으로 바꾸지 않는다.
- **부정·부분**: 전면 부정과 부분 부정, 모두·각각·적어도·만·일부, 및·또는, 항목별 값과 합계를 보존한다. 못 했다·안 했다의 원인을 근거 없이 확정하지 않는다.
- **주체**: 행위자, 대상, 수신자, 소유를 보존하고 주체가 바뀌면 이름을 쓴다. 시스템 자동 처리와 독자 행동을 구별한다. 원문 작성자가 독자에게 보고한 실행을 편집자의 새 실행 주장으로 바꾸지 않는다.
- **단계**: 준비·요청·실행, 시작·진행·완료·중단을 유지한다.
- **조건**: 조건, 예외가 면제하는 대상, 기본·우선, 비교 방향을 유지한다. 선택적 행동은 원문의 조건부 시점과 함께 둔다. 서로 이웃한 권고와 후속 가능 행동을 새 조건문으로 연결하지 않는다. 원문에 없는 ‘~했다면’·‘~해야만’을 넣지 않는다. 권고와 후속 가능 행동은 각각 보존한다.
- **수치·시간**: 대상, 단위, 정밀도, 경계와 약·최대·평균·기본값의 성격을 보존한다. 반복 주기, 처리 시간의 실측 표본, 지연 상한, 운영 시간, 종료 조건은 서로 다른 사실로 둔다. 원문이 주장한 상한과 허용은 삭제·강화·약화하지 않는다. 근거 없는 새 숫자나 보장을 만들지 않는다.
- **모순**: 원문 안의 모순을 임의로 해소하지 않는다. 양쪽을 남기거나 불일치를 밝힌다.

미표기, 미확인, 확인된 부재를 구별한다. 원인, 시험, 수치, 담당자, 날짜, 후속 약속을 명료화를 이유로 더하지 않는다. 편집 결과를 알릴 때는 실제로 한 변경만 쓴다.

## 보존과 일관성

인용, 코드, 명령, 경로, 링크, 버전, ID, 공식 명칭, 파일명, 수치 문자열은 부호·대소문자·공백까지 그대로 둔다. 오탈자처럼 보여도 고치지 않는다.

안전 표지, 위험 등급, 조건부 허용과 전면 금지의 구분을 바꾸지 않는다. 경고는 위험 행동 앞에 둔다. 주석·팁에 있는 필수 행동, 안전 조치, 필수 요구조건, 허용 한계는 본문 절차나 사양으로 옮긴다.

같은 대상에는 같은 명칭을, 같은 행동에는 같은 동작어를 쓰고 같은 문맥에서 한 용어는 한 뜻으로 쓴다. 낯선 줄임말은 처음 나올 때 전체 명칭을 붙인다. 지시어나 생략된 대상의 후보가 둘 이상이면 확인된 대상명을 쓴다.

같은 범위의 반복만 합친다. 전체에 대한 주장과 특정 기능·단계에 대한 주장은 겹쳐도 각각 보존한다. 특정 기능의 사례만 남겨 전체 주장을 대신하지 않는다. 단계·기산점·조건이 다른 사실은 합치지 않는다. ‘끝나면’ 같은 원문의 기산 사건을 확인되지 않은 특정 도구·작업의 종료로 바꾸지 않는다.

## 문서 구조

### 결과·완료 보고

결과·완료 보고에만 이 틀을 쓴다. 첫머리에는 완료 대상과 접근 위치만 짧게 둔다. 운영 시간·주기·조건을 도입 문장에 한꺼번에 넣지 않는다. 바로 다음 첫 실질 블록에 사전 권한·접근 조건, 사용 가능 조건, 운영 필수조건, 사용 중 계속 지킬 조건, 운영 시간, 공유·노출 범위를 둔다. 운영 시간, 확인 주체, 확인 주기는 각각 이름 붙은 독립 행으로 둔다. 녹음·수집 간격과 분석·확인 주기는 같은 값이어도 별도 속성이다. 보고된 지연과 그 원인의 관계는 유지하되, 확인 주기 행과 지연 행을 구별한다. 기능 상세, 설계 근거, 제작 경과, 도구 사용 설명은 그 뒤에 둔다. 사용 제한은 실패 판정으로 바꾸지 않는다. 최종 사용을 막는 실패가 원문에 있을 때만 그 실패를 결과로 앞세운다. 성공과 실패는 대상·단계·검증 수준별로 나누고, 원문에 없는 최종 판정은 추론하지 않는다.

남은 조치와 사용·미팅 종료 후 할 행동은 기능 설명이나 설정 변경 이력과 분리하고, 해당 시점의 후속 행동 묶음에 모은다. 권고·가능·의무의 차이는 유지한다.

### 대상별 행동 안내

행동 대상이 여럿이면 첫 본문 블록에서 대상을 하나씩 별도 불릿으로 나열한다. ‘대상: A, B, C’처럼 한 행에 합치지 않는다. 공통 담당·기한은 목록 다음에 둔다. 대상별 행동이 다르면 각각 구분한다. 모두·하나, 필수·선택 관계는 도입부에 원문대로 쓴다.

### 방식 비교

선택지마다 제목을 두고 그 아래 속성을 불릿으로 둔다. 원문에 없는 속성은 만들지 않는다. 모든 선택지에 적용되는 규칙은 별도의 동급 제목으로 분리한다.

### 절차

성격이 다른 항목은 한 번호 목록에 섞지 않고 블록을 나눈다. 안내→응답→미응답 시 후속 처리처럼 실제 시간 순서가 있으면 번호 절차로 쓴다. 자동 처리도 그 단계의 주체를 밝혀 같은 순서에 넣는다. 절차를 속성별 불릿으로 바꾸지 않는다.

- **사전 준비**: 시작 전에 갖출 것
- **상시 유지 조건**: 사용하는 동안 계속 지킬 것
- **순차 행동**: 실제 선후가 있을 때만 번호를 붙인다. 단계마다 따로 확인할 행동 하나를 두고 실행 동사로 끝낸다.
- **선택적 권고**: 원문의 조건부 시점과 함께 둔다.

원문이 여러 단계에 적용한다고 확인한 조건만 도입 줄에 둔다. 앞 조건을 후속 단계로 확대하지 않는다. 예외는 면제하는 조건 옆에 둔다. 전·후·동안·동시 관계를 드러낸다. 짧은 조건 하나와 행동 하나는 한 문장으로 둘 수 있다.

### 설명·교육

이해 순서를 따르고 뒤 설명의 전제가 되는 정의를 먼저 준다. 직접 답을 요구한 질문에는 답부터 준다.

## 기한

기한은 관련 행동 블록 안에 '○○ 기한: 원문 시간 구절'로 독립 표시하고 수행자와 행동은 다음 줄에 둔다. 기산 사건, 경계, 영업일 여부, 기본 기한과 예외 기한의 대체 관계를 원문대로 보존한다. 새 날짜·시간대·휴일 계산을 만들지 않는다.

## 형식 선택

사용자가 지정한 형식이 우선한다. 그다음 행동 대상 목록과 순차 절차 규칙을 먼저 적용한다. 아래 속성 행은 그 밖의 사양·기능·상태·비교 설명에만 적용한다. 별도 지정이 없고 대상에 독립 속성이 둘 이상 있으면 **대상 제목 + 속성별 행**으로 작성한다. 한 행의 형식은 `- 속성명: 해당 값·행동·조건`이다. 비교할 때는 `속성 | 값` 표를 써도 된다. 속성명으로 답을 바로 찾게 하며, ‘내용·상세·구성·변경’ 같은 포괄 이름 아래 여러 속성을 다시 모으지 않는다.

수량, 정렬, 검색 범위, 위치, 총액, 차액, 규격, 방식, 대수, 계산 대상, 기준량, 기준 시간, 입력된 필드, 빈 필드는 서로 다른 질문이다. 원문에 있는 속성만 각각 별도 행으로 만든다. 한 항목에 다른 단위의 수치가 여럿 있거나 동작과 수량이 함께 있으면 독립 속성인지 다시 나눈다. 같은 역할의 필드 이름을 나열한 값이나 하나의 값과 단위·조건은 함께 둔다. 장비·제품 이름을 속성명으로 삼아 규격·방식·대수를 한 값에 합치지 않는다. 변경 전후가 있는 속성은 해당 행 안에서 변경 방향을 보존한다. 예컨대 한 계산의 대상·기준량·기준 시간도 같은 제목 아래 각각 이름을 붙여 관계를 유지한다. 원인과 결과, 조건과 행동을 나눌 때는 관계를 명시한다. 행을 떼어 읽어도 적용 범위가 같아야 한다. 특정 기능의 사용 여부를 전체 시스템의 사용 여부로 넓히지 않도록 행 이름에 범위를 쓴다. 새 제목·속성명도 주장이다. 원문이 확인하지 않은 작동 범위·정렬 대상·선후·인과를 이름으로 추가하지 않는다. 속성별 행을 쓴 뒤 같은 내용을 설명 문장으로 반복하지 않는다.

속성 분리 예시(가상 수치이며 원문에 적용하지 않는다):
- 묶인 표현: 장치가 40W에서 25W 수랭식 2대로 바뀌었다.
- 분리 결과:
  - 소비전력 변경: 40W → 25W
  - 변경 후 냉각 방식: 수랭식
  - 변경 후 대수: 2대

절차는 앞 절의 번호 규칙을 따른다. 짧은 상태 하나나 짧은 조건 하나와 행동 하나는 문장으로 둔다. 독립 속성이 없는 설명 문장까지 기계적으로 쪼개지 않는다.

출력 전에 초안을 다시 읽는다. 아래 결함이 보이면 최종 본문에서 고친 뒤 제출한다. 점검 과정과 통과 여부는 출력하지 않는다.
- 한 행이나 불릿이 둘 이상의 질문에 답한다. 특히 대상만 목록화하고 수량·위치·정렬·규격·계산 기준을 그 뒤 문장에 몰아넣었다.
- 조건·절차만 나누고 다른 속성은 한 덩어리로 남았다.
- 나누면서 값과 단위, 조건과 행동이 떨어졌다.
- 결과 보고에서 사전 권한이나 유지 조건이 첫 실질 블록 밖에 있다.

상태·결과·표제는 대상·범위·양태가 명확하면 짧은 명사형으로 쓸 수 있다. 요청과 실행처럼 행동·시점을 바꾸는 축약은 하지 않는다. 핵심 조건은 괄호에 숨기지 않고, 슬래시나 세미콜론만으로 조건·선택·인과를 나타내지 않는다. 새 정보 없는 제목·예고·맺음말·요약과 작성 과정 설명은 넣지 않는다.

## 조회 자료

`specification/rules.json`, `lexicon/core.json`, `lexicon/domains/software.json`은 활용형, 조사 패턴, 전문어 등록, 사용 중단 표현 같은 드문 판단에만 해당 항목을 조회한다. 일반 작성에는 읽지 않는다. 조회하지 않았으면 등록 여부나 규칙 충족을 확인했다고 말하지 않는다. 미등록이라는 이유만으로 금지하지 않는다.
